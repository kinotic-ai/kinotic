Kinotic OS

Organization Management

How organizations are created, how their users authenticate, and how OIDC providers are wired up.

Overview

A Kinotic deployment hosts many customer organizations. Each org has its own users, applications, and (optionally) its own enterprise SSO configuration. This page describes how an org is created, who can log in to it, and how the OIDC plumbing is shared across orgs without leaking access between them.

System users sign in to the system server, separately from everything described here; see System Authentication.

Mental Model

Eight persistent entities carry the auth state, and a short-lived entity bridges each signup. The Sign-In Design reference draws them and the flows between them.

An application signs in through the system's Google and Microsoft registrations with an ApplicationOidcConfiguration of that kind whose clientRegistrationType is MANAGED; switching it to OWN with the organization's own client ID and secret is an edit of the same configuration, and its users stay the same users.

An ApplicationSocialOidcConfiguration is never offered on its own: it is the credentials a MANAGED application configuration signs in through. The roles are separate subtypes of OidcConfiguration, stored in one index under a type discriminator the way the kinds of ParticipantIdentity are, rather than one type with a flag, because the difference between them is ownership. Every lookup filters on the discriminator and every write is held to its kind's owner, so an org admin configuring SSO can never make it appear as a global button or name a system secret, and a seeded system registration can never affect an org's SSO settings.

Org Creation

There are two entry points, both producing an Organization and an admin ParticipantIdentity scoped to it. The SPA's /signup page currently offers GitHub only (a hardcoded button — every Kinotic project is backed by a GitHub repository, so the founding user signs up with GitHub and installs the GitHub App right after). The email/password signup entry point remains fully mounted on the backend; its previous UI (Signup.vue) is kept in the tree unrouted until other methods return. Login is not restricted: invitees must be able to sign back in however they joined, so an organization's login page keeps every provider the organization offers plus a password form.

Email/password signup (backend flow — not currently reachable from the SPA)

1. User loads /signup, enters email + displayName
2. POST /api/auth/org/signup
3. SignUpService.initiateLocalSignUp:
   - rejects if a sign-up is already pending for this email, or if an organization user
     already exists for this email: a person founds one organization at most, and joins
     others by invitation. When that organization user is a member an administrator added
     that nobody signs in as yet, the refusal (PendingMemberException) says to accept the
     invitation or sign in on that organization's sign-in page
   - creates a PendingSignUp with a 24h verification token
   - EmailService sends the verification link (logs it instead when email is disabled), which
     opens the portal
4. User clicks /signup/verify?token=<verificationToken> in their inbox
5. /signup/verify form (VerifyEmail.vue) prompts for orgName + password + confirm
6. POST /api/auth/org/signup/complete  { token, orgName, orgDescription?, password }
7. SignUpService.completeLocalSignUp:
   - validates token, rejects if expired
   - creates Organization (auto-derived id from name)
   - creates the founder's organization user (OrganizationParticipantIdentity,
     enabled=true) with an IdentityCredential (bcrypt hash, separate index keyed by the
     organization user's id)
   - creates the founder's OrganizationMembership of the organization
   - links Organization.createdBy = the organization user's id
   - deletes the PendingSignUp
8. The gateway establishes the browser session (204 + Set-Cookie); the frontend then calls
   userState.login() to open the realtime connection, authenticated by that session cookie.

Email verification is the security gate — no Organization, organization user or membership exists until the link is clicked. With KINOTIC_EMAIL_ENABLED=false (the local default) the verification URL is logged to the management server's console instead of sent; copy it into the browser to finish the flow.

Social-IdP signup

1. User loads /signup, clicks "Sign up with GitHub" (the page's only button today)
2. POST /api/auth/org/signup/social/start/github
3. OrganizationSignupHandler.handleSocialStart:
   - picks the OrgSignupOidcConfiguration whose provider key matches
     (oidcConfigurationService.findEnabledOrgSignupByProvider)
   - generates state/nonce/PKCE, stashes them on the session cookie
   - 302 to <authority>/authorize?...
4. User authenticates at the IdP
5. IdP returns to GET /api/auth/org/login/social/callback/<configId>, the one callback the
   registration is registered with; the flow's purpose, recorded at its start, routes it
6. OrganizationOidcCallbackHandler → OrganizationSignupHandler.complete:
   - validates state/nonce/PKCE, exchanges code for id_token + access_token
   - rejects if email_verified=false in the id_token
   - SignUpService.createOidcPending rejects with user_exists if an organization user is
     already bound to (configId, sub) or holds the verified email: a person founds one
     organization at most, and joins others by invitation. It rejects with user_pending when
     that organization user is a member an administrator added that nobody signs in as yet,
     who gets in through their invitation or the organization's own provider. SignUpService
     checks again at completion, so two sign-ups of one identity
     in flight at once cannot both found an organization, and the organization is never
     created for an organization user that cannot be
   - creates a PendingSignUp with the verified subject, configId, email, displayName
   - 302 to /register?token=<verificationToken> on the UI the sign-up started from, when
     kinotic.cors.allowedOriginPattern names its origin other than through *, and on the portal otherwise
7. /register prompts for orgName (CompleteOrg.vue)
8. POST /api/auth/org/signup/social/complete  { token, orgName, orgDescription? }
9. SignUpService.completeOidcWithNewOrg:
   - validates the pending token
   - creates Organization
   - creates the founder's organization user (enabled=true) with an OidcBinding of
     (configId, sub) to it
   - creates the founder's OrganizationMembership of the organization
   - links Organization.createdBy
   - deletes the PendingSignUp
10. The gateway establishes the browser session (204 + Set-Cookie). CompleteOrg.vue then
    calls userState.login() to open the realtime connection, authenticated by that session
    cookie. No token travels in the URL.
11. CompleteOrg.vue shows a "Connect GitHub" step explaining that the next GitHub
    round-trip authorizes repository access (distinct from the sign-in, which only
    proved identity). Clicking "Continue to GitHub" calls
    githubAppInstallations.startInstall("/") and redirects the whole tab to
    the returned GitHub install URL. The App requests user authorization (OAuth) during
    installation, so GitHub returns to the management server's /api/github/install/callback
    — the App's first registered callback URL — with code, installation_id, and the state
    minted by startInstall, and that route forwards them to the portal's
    /github/install/callback. The callback runs completeInstall, which consumes the state, exchanges
    the code with the github-platform credential for the authorizing user's access
    token, and binds the installation only when GitHub's /user/installations reports
    that user can access it (see [Defense in Depth](/platform/defense-in-depth)). It
    then lands on / — project creation requires the install, so the new org arrives
    ready. If the install can't start, the page falls back to / directly. The portal's /
    opens the Quickstart until the organization has its first project, and Applications
    after that.

Another UI signed in through the management server, such as one built on Kinotic, links GitHub without the portal: it calls startInstall with the absolute URL of one of its own pages as returnTo, which must be on an origin kinotic.cors.allowedOriginPattern names (a pattern of * names none); startInstall refuses any other URL, and a network-path reference (a returnTo starting with // or /\). After the install, /api/github/install/callback forwards GitHub's installation_id, state and code to that page as query parameters, and the page calls completeInstall itself.

The PendingSignUp is consumed once. The ?token= in the redirect to /register is the short-lived PendingSignUp verification token. It is not a login, which the session cookie set when the org-naming POST succeeds establishes, but whoever holds it can found the organization as the verified identity, so it is handed only to a UI the CORS pattern trusts.

GitHub follows the same flow with one difference in step 6: GitHub is OAuth 2.0 only and issues no id_token, so its configuration row sets the endpoints explicitly instead of relying on discovery — authorizationUri/tokenUri drive the code flow, userInfoUri supplies sub and the display name, and userEmailsUri supplies the email plus its verified flag (primary address preferred). Any curated row that sets these fields takes this path; nothing about it is GitHub-specific in code, and only a curated row can set them. Issuer, audience, and nonce validation don't apply (there is no token to carry them); the state match and the direct TLS code exchange are the security boundary.

Members

An organization's administrators add its members on the Members page, one action for every case: Add member, with the person's email, an optional display name and a switch, on by default, that sends them an invitation email (MemberService.addMember(email, displayName, sendInvitation), Kinotic.members.addMember).

  • An address with no organization user yet gets one, with no sign-in method, and its membership at once, so the person appears among the members as Pending. With the switch on, the invitation they receive claims the organization user: they set a password, or sign in through one of the organization's providers under the same address. With the switch off, nothing is sent and the person signs in through one of the organization's own providers (OrganizationOidcConfiguration), whose first sign-in under the invited address claims the organization user — so the switch can only be off when the organization has one, and the server refuses the request otherwise, revealing nothing about the address.
  • An address that already has an organization user is emailed an invitation whatever the switch says, since joining someone's organization user to an organization needs their acceptance; they appear once they accept, and the administrator is told an invitation was sent. Accepting with that organization user's password, or through one of the organization's providers whose verified email is the invited one, joins it. A system user or an application's user with the same address is a different identity, which neither the invitation nor the member list sees: the address joins as a new organization user with a password of its own.
  • Pending members are listed with the invitations alike, each with Send invitation (MemberService.sendInvitation(email), which sends the one they have again or a new one for a member added without) and Remove. Removing a pending member deletes the organization user nobody signed in as and the invitation it never accepted; removing a member who has signed in leaves their organization user and other organizations as they are.
  • An application's users are still invited (MemberService.inviteMember(email, displayName, applicationId)), since their rows belong to the application and are created when the invitation is accepted.

Email templates

The portal's invitations and verification links open the portal and use Kinotic's own emails. A server that embeds Kinotic's modules to serve a UI of its own sends them in that UI's name instead, by passing an EmailTemplate in process: management-api's MemberInvitationService.addMember, sendInvitation and inviteMember (the calls MemberService makes, run as the organization user bound to the call) and kinotic-domain's SignUpService.initiateLocalSignUp. EmailTemplate is not part of any published service, so no gateway connection can choose one.

A template's uiBaseUrl is the UI whose /invite/accept?token= or /signup/verify?token= page its link opens, with no trailing slash, and its subject, htmlBody and textBody are Handlebars sources rendered with the email's variables. A call that would send an email with a template whose uiBaseUrl is not an absolute http or https URL naming a host, without user info, a query, fragment or trailing slash, or whose source is missing or does not compile and render, fails with IllegalArgumentException before it saves anything. Write a URL variable in the HTML with triple braces, such as {{{acceptUrl}}}, so it is not HTML-escaped.

EmailVariables
An invitation into an organization or one of its applicationsinviterName, organizationName, applicationName (absent for an organization invitation), acceptUrl, expiresInDays
A sign-up with email and passworddisplayName, verificationUrl

That UI's invitation page calls the /api/auth/invite/* routes below. An acceptance through a provider returns to the page that started it, and a failed one to that page's /invite/accept?error=, when that page is the portal or kinotic.cors.allowedOriginPattern names it, and to the portal otherwise. An application invitation whose application has its own invitation template is sent with that template's content, and its link still opens the passed template's UI.

The Members page lists the organization's members as OrganizationMember rows (MemberService.findMembers / searchMembers): each joins an organization user with its membership, so enabled is the membership's standing, joined its creation, and pending marks a member who has not signed in yet. An application's Users page lists the application's users themselves, ApplicationParticipantIdentity rows (MemberService.findApplicationUsers / searchApplicationUsers), whose standing is the user's own.

An organization's own provider therefore signs in only the members its administrators added: a person the provider verifies whose address no pending member holds gets no_user, and createUserOnSignIn is refused on an OrganizationOidcConfiguration. Nothing an organization's provider asserts can reach an organization user the organization did not create, and an organization user someone already signs in as joins only by its holder's acceptance.

User Login

A login is addressed to an organization. An organization user may be a member of any number of organizations, each an OrganizationMembership of its own, so nothing about the person alone says where they are signing in; the organization's id, the slug of its hostnames (see Applications and Projects), is what every login route and page is addressed by. The portal has two login pages:

  • /login, the landing page, for someone whose organization is not yet known: the system's social buttons, which sign in without naming an organization when the identity belongs to exactly one and otherwise offer the ones it belongs to; an organization field that leads to that organization's page; and a "Don't know your organization?" link that emails the person the organizations their address belongs to.
  • /login/<organizationId>, the organization's page (OrganizationLoginPage.vue), which offers exactly what that organization's login supports: one button per configuration GET /api/auth/org/login/<organizationId>/providers lists — the system's org sign-up registrations (GitHub) followed by the organization's own OrganizationOidcConfigurations — and an email + password form. The organization's own host, <organizationId>.<sitesDomain>, redirects here.

The browser remembers, in localStorage, the organization it last signed in to, whichever method signed it in: password, GitHub, an organization's own provider, sign-up, an accepted invitation or a switch of organizations. A returning browser that opens /login is sent on to that organization's page, keeping the query and so the referer. The landing page stays put when nothing is remembered, and when its query carries ?error=, so a failed sign-in or a choice of organizations is shown there; its organization field is then prefilled with the remembered organization. The organization page's Not your organization? link forgets the remembered organization before it returns to /login, so the landing page stays put; it is also the way out when the remembered organization no longer exists and the page says there is no organization by that name.

No route asks about an email first: the page offers every method up front, and the password login answers a generic 401, so nothing tells whether an email has a user anywhere. What the page does disclose, to anyone who knows an organization's id, is that the organization exists and the names and provider kinds of the configurations its login offers, as any SSO login page does; the id is already public as the organization's hostname, and the configurations are the buttons the page shows. A signed-in member of several organizations switches between them without signing in again: the account menu's Organizations list posts POST /api/auth/org/switch { organizationId }, which re-establishes the session for the chosen membership and reloads the portal.

Password

The form posts email + password to the organization's login route, which verifies the credential and establishes a browser session — there is no client-held token. The fetch uses credentials: 'include' so the gateway's Set-Cookie is stored even cross-origin:

1. POST /api/auth/org/login/<organizationId> { email, password }   (credentials: 'include')
2. OrganizationLoginHandler.handleLogin → AuthEndpointSupport.handlePasswordLogin:
   - LocalAuthenticationService.authenticateOrganizationUser(email, password)
       finds the organization user with that email (a system user or an application
       user with the same email is another row and never signs in here), requires it
       enabled, loads its IdentityCredential and verifies the bcrypt hash; an
       organization user with no password fails here
   - ParticipantIdentityService.resolveParticipant(user.id, organizationId, null)
       requires the organization user's enabled OrganizationMembership of that
       organization and makes the OrganizationParticipant from the two
   - on success: establishSession(ctx, participant) puts it on the Vert.x session
                 (regenerating the session id), then 204 + Set-Cookie
   - on any failure: 401 "Invalid credentials"
                     (deliberately generic — covers unknown email, wrong password,
                      no password, disabled user or membership, not a member)
3. OrganizationLoginPage.vue calls userState.login() → Kinotic.connect().
   The default resolution supplies no auth headers in a browser, so the
   WebSocket upgrade is authenticated by the session cookie set in step 2.

The SPA never exchanges the password for a token and never sends raw passwords over the WebSocket. Non-UI clients (CLI, automation) do not use this path — they authenticate directly at the upgrade instead; the table in "The WebSocket upgrade" below covers what each client type presents.

A provider the organization offers

Each button on the organization's page is a form posting to the organization's start route for that configuration. The route also answers GET, so a link — from a bookmark, or from the organization's own tile in its provider's application launcher — starts the same flow:

1. POST|GET /api/auth/org/login/<organizationId>/start/<configId>?referer=<spa-path>
   - the router guard bounced an unauthenticated navigation to /login?referer=<spa-path>,
     and the login pages forward it here; a provider sign-in leaves the SPA, so the path
     cannot be kept client side the way the password path keeps it
2. OrganizationLoginHandler.handleStart:
   - an enabled OrgSignupOidcConfiguration under that id, which every organization's
     login offers; otherwise the organization's own configuration under it
     (oidcConfigurationService.findOffered(configId, organizationId, null)); 400 for
     anything else
   - stashes the organization on the flow session, with the referer when it names a
     path within the SPA, then state/nonce/PKCE as for signup, and 302 to the IdP
   - the completed login is bound to the page that started it, or to the portal when a
     GET link, which names no page, started it; a page that is neither the portal nor one
     kinotic.cors.allowedOriginPattern names is not recorded, and the flow returns to
     the portal holding no login for it
3. IdP returns to the callback registered for the configuration:
     GET /api/auth/org/login/social/callback/<configId>   an org sign-up registration
     GET /api/auth/org/login/sso/callback/<configId>      the organization's own configuration
4. OrganizationLoginHandler.completeOrganizationLogin:
   - validates state/nonce, exchanges code, validates id_token (sub + email_verified)
   - looks up the organization user bound to (configId, sub) (ParticipantIdentityService.
     findOrganizationUserByOidcIdentity) and its OrganizationMembership of the stashed
     organization
   - no organization user bound to the identity: through the organization's own
                 configuration, the member an administrator added under the identity's
                 verified email that nobody has signed in as yet is claimed — the identity
                 is bound to that organization user as its first sign-in method and it
                 signs in; otherwise 302 /login?error=no_user
   - no membership: 302 /login?error=no_user
   - a disabled organization user or membership: 302 /login?error=user_disabled
   - otherwise: establishSession(ctx, participant), then redirectSuccess → 302 to the
       stored referer, or the SPA root when the flow stored none, with Set-Cookie.
       No token travels in the URL.
5. The SPA loads with the session cookie set; userState.login() opens the realtime
   connection, authenticated by that cookie.

Social button on the landing page

The landing page's buttons are populated from GET /api/auth/org/login/providers, which lists the unique provider keys present in the org sign-up configs (the invite-hint UI on MembersPage reads the same endpoint). A sign-in there names no organization, so its callback finds the one organization the identity is a member of:

1. POST /api/auth/org/login/social/start/github?referer=<spa-path>
2. OrganizationLoginHandler.handleSocialStart:
   - finds the OrgSignupOidcConfiguration with provider="github"
     (oidcConfigurationService.findEnabledOrgSignupByProvider)
   - same flow-session setup as above, with no organization stashed, then 302 to the IdP
3. IdP returns to GET /api/auth/org/login/social/callback/<configId>
4. OrganizationLoginHandler.completeLandingLogin:
   - finds the organization user bound to (configId, sub) and its enabled memberships
     (OrganizationMembershipService.findMemberships)
   - exactly one: signs in to that organization as above
   - no organization user, or no membership: 302 /login?error=no_user
   - a disabled organization user, or one whose every membership is disabled:
     302 /login?error=user_disabled
   - several: their ids are kept in the session for the page that started the flow and
     302 /login?error=multiple_organizations&referer=<spa-path> — the user has proven who
     it is, so the landing page reads the ids from GET /api/auth/org/login/choices, answered
     for two minutes and until the page starts a login at an organization, and offers those
     organizations to choose from; the person signs in at the chosen one's own page, which
     lands on the referer. The redirect carries no ids, so the page that started the flow
     learns only the code

Finding one's organizations

POST /api/auth/org/login/find { email, turnstileToken } emails the address every organization its organization user holds an enabled membership of, each with a link to that organization's login page (OrganizationService.sendMembershipsEmail); a disabled organization user is told of none, as it can sign in to none. The route always answers 204 and the email is sent whether or not the address belongs to any organization — one that belongs to none says so — so the request reveals nothing about the address. With KINOTIC_EMAIL_ENABLED=false the links are logged to the management server's console instead of sent.

The route is open to anyone and sends an email on every call, so it requires a person at the browser: a Cloudflare Turnstile token earned on the page, verified by the management server with the site's secret (TurnstileVerifier, configured under kinotic.managementServer.turnstile.*). GET /api/auth/org/login/find answers {turnstileSiteKey}, the site whose challenge the landing page renders before it enables the button, and a request whose token is missing, already verified or refused answers 400. An environment with no Turnstile site, such as the e2e stack, turns the requirement off with kinotic.managementServer.turnstile.enabled=false, and the GET answers {}; development uses Cloudflare's always-passing test site.

System users (SYSTEM scope)

A system user is a SystemParticipantIdentity (type SYSTEM_USER): unique by email among system users, acting in the system scope alone. The same email may also be an organization user and a user of any application, each with its own password. System users sign in through a separate, password-only route used by the system console (there is no signup, SSO, or social path for SYSTEM scope):

1. POST /api/auth/system/login { email, password }   (credentials: 'include')
2. SystemLoginHandler.handleLogin → AuthEndpointSupport.handlePasswordLogin:
   - LocalAuthenticationService.authenticateSystemUser(email, password)
       verifies the system user's password, then resolveParticipant(user.id, null, null)
       makes its SystemParticipant — an organization user or an application user, even
       with the same email, is another row and can never authenticate here
   - success/failure behave exactly like the org password branch:
     204 + Set-Cookie, or a generic 401

The session established here is the same browser-session mechanism as every other login path; /api/auth/me and /api/auth/logout apply unchanged.

The console lists them at Members → Users, read-only, from SystemMemberService.findUsers in the system zone, which lists the SystemParticipantIdentity rows. System users are created outside the console — by the migration fixtures, or by the identity provider once SYSTEM scope is behind Entra — so the page reports who holds access rather than granting it.

The WebSocket upgrade (the final step in every path)

Authentication happens at the WebSocket upgrade (handshake), not in a STOMP CONNECT frame. How the upgrade is authenticated depends on the client:

ClientUpgrade credentials
Browser SPASession cookie established by the REST login; the default credential resolution supplies no headers
Node client, credentialsclientId, clientSecret, plus organizationId / applicationId scope headers (via BasicCredentialsResolver or the KINOTIC_CLIENT_* environment variables)
Node client, Bearer tokenAuthorization: Bearer <jwt> (via BearerCredentialsResolver); a Kinotic JWT carries the organizationId / applicationId claims

The browser SPA never holds a JWT — its login establishes a session cookie and that cookie authenticates the upgrade. The Bearer path is for non-browser clients: the CLI obtains an access token through the OAuth device-code grant at POST /api/auth/oauth/token, which mints a Kinotic JWT carrying sub / email / organizationId / applicationId. For that path the management server validates the JWT signature against its signing keys and creates the Session. Every path admits only the server's own kind of participant: a credential that proves an identity of another scope fails as invalid (see System Security). The CLI persists a rotating refresh token to mint fresh access tokens before each connect.

Provider-Specific Quirks

OIDC is a standard, but providers diverge on a few details. The validation helpers in OAuth2Util (isIssuerValid, isEmailVerified) handle these declaratively — the provider key on OidcConfiguration selects the right behaviour. No provider needs handler-level branching: a row either has an authority for OIDC discovery — derived from the organization's providerAccount for an organization's row, seeded for a curated one — or, for a curated row only, sets authorizationUri/tokenUri/userInfoUri/userEmailsUri/scopes explicitly, and every handler consumes the same claims shape either way.

Per-Org SSO Configuration

An OrganizationOidcConfiguration is offered at the org's own login page, /login/<organizationId>, by existing. An organization admin manages the organization's configurations in the portal under Organization settings → Authentication providers, or through the published OwnedOidcConfigurationService the page calls (Kinotic.ownedOidcConfigurations in @kinotic-ai/management-api, and an MCP tool), which acts for the caller's organization alone.

  1. Add provider opens the form in a drawer on the right. Pick the provider (Google, Microsoft or Okta) and enter the display name the login page prints on its button, the organization's account at the provider where the kind takes one (the Directory (tenant) ID for Microsoft Entra ID, never common or organizations, which an application's provider may name, the Okta domain on okta.com, oktapreview.com or okta-emea.com for Okta), the client ID and the client secret, or tick Public client (no secret). The form checks the account against the kind's pattern before it saves, and shows the server's message when the server still refuses. The audience is optional, under Advanced. Saving calls OwnedOidcConfigurationService.save(configuration, clientSecret): the authority is derived from the kind's template, so no URL is given, and the organizationId is the caller's whatever was sent. A secret is held in the organization's own scope of the secret storage — the row itself never names one, and nothing reads it back through the service; confidentialClient says whether one is held. createUserOnSignIn is refused on an organization's configuration, and the form does not offer it: the organization's administrators add its members (see Members), and the provider signs in the member it verifies under a pending member's address, claiming that organization user on the first sign-in, or the organization user its identity is already bound to. A person the provider verifies whose address is no member's gets no_user; one whose address already has an organization user that someone signs in as is not claimed, and joins by accepting the invitation the administrator's Add member sent.
  2. Once saved, the form shows the configuration's callback URL, <kinotic.managementApi.apiBaseUrl>/api/auth/org/login/sso/callback/<configId>, which OwnedOidcConfigurationService.findCallbackUrl(configId) returns. Add it to the IdP app registration as a redirect URI; sign-ins through the configuration fail until it is there. It is the only one the configuration needs: a login, an invitation accepted through the provider, and a member connecting the provider to their organization user from the Profile page all return to it, and the flow's purpose, recorded on the session when it starts, says which it is. For a same-origin deploy that base is the portal's own origin; for a split-origin deploy (the SPA on the sites Worker, the backend on AKS) it is the backend's hostname, so the IdP returns the browser to the management server, not the SPA. The provider's row, its Edit form and its details all show the same URL again.
  3. Editing a configuration leaves its kind fixed, since the kind is the scope it is offered at and the server refuses a save that changes it. The client secret field starts empty: a save with it empty keeps the secret held (save with a null or blank secret keeps it), and a secret entered replaces it. Make this a public client, which asks for confirmation, deletes the held secret with OwnedOidcConfigurationService.deleteClientSecret(configId).
  4. The row menu also enables or disables the configuration (a disabled one is listed on no login page and signs no one in), deletes it after a confirmation (sign-ins through it stop at once and its held secret is deleted), and copies it to an application: Copy to application calls OwnedOidcConfigurationService.copy(configurationId, applicationId), which makes an ApplicationOidcConfiguration with the source's provider, account, client ID and secret, and shows the copy's own callback URL, <the application's API host>/api/auth/app/login/oidc/callback/<copyId>, to register with the provider as well. The application's API host is its label under kinotic.domain.appApiBaseUrl.

A user who logs in via this path lands at the /api/auth/org/login/sso/callback/:configId handler — the IdP doesn't care that the configId is org-scoped instead of system-scoped. The provider's application launcher can link straight to <kinotic.managementApi.apiBaseUrl>/api/auth/org/login/<organizationId>/start/<configId>, which starts the same flow from a plain GET; the form and the row's details show it as the Direct sign-in link.

System Authentication

System users (SystemParticipantIdentity) sign in to the system server with an email and password, POST /api/auth/system/login, and the plan is to move it to Microsoft Entra, separate from the routes documented above. The system login authenticates system users alone, so an organization user is refused there as a wrong password is, and every organization login authenticates organization users alone, so a system user is refused there the same way. A person who is both signs in to each with that scope's own user and password. The curated social providers are intentionally limited to end-user self-service signup and grant org-scoped access only, so no organization route can produce a SYSTEM-scoped session.

The app server serves every application at an API host of its own, <organizationId>--<applicationId> under kinotic.domain.appApiBaseUrl (see Configuration). Its login and OAuth routes act for the application whose host the request is addressed to and answer 404 on any other host, and that host is the application's OAuth issuer. The one exception is a sign-in through a system social registration (ApplicationSocialOidcConfiguration): a provider returns the browser only to a redirect URI registered in advance, and the registration is shared by every application that offers it, so its authorize and callback routes are served at kinotic.domain.appApiBaseUrl itself, the shared host, and the verified sign-in is handed to the application's own host under a single-use code (SocialLoginHandoffService, an Ignite cache with a one-minute TTL) where the session is established. The code completes the sign-in only in the browser that started it: the start at the application's host put a value in that browser's session, the shared host carries it through its own session into the handoff, and the completion requires the browser to present it again, so a completion URL passed to another person signs no one in.

CORS for the server's UI origin is applied at the router root. A Vert.x SessionHandler covers every /api/* route (and the STOMP WebSocket path), so the same session cookie carries the OIDC roundtrip state and the post-login identity; the cookie is HttpOnly, Secure, SameSite=Lax, with a configurable timeout (kinotic.api-gateway.session-timeout).
