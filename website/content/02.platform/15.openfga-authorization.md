## Activation and rollout

The implementation is opt-in. Set the same authorization configuration on every gateway and persistence node in the cluster:

```yaml
kinotic:
  authorization:
    enabled: true
    endpoint: http://openfga:8180
    api-token: ${OPENFGA_API_TOKEN}
    check-timeout: 50ms
    publication-timeout: 10s
    bootstrap-system-identity-ids:
      - ${AUTHORIZATION_BOOTSTRAP_OPERATOR_ID}
```

A bootstrap identity must be an authenticated **SystemParticipant** whose persisted identity ID is explicitly configured. An organization user cannot become an operator by supplying this ID in an argument. Without a published policy, ordinary requests are denied. Initialization and recovery run through the system server's service API, with its configured operator session:

```ts
await Kinotic.accessControl.initialize({
  kind: AuthorizationScopeKind.ORGANIZATION,
  organizationId: 'acme'
}, firstOrganizationAdministratorIdentityId)
```

Organization initialization is operator-only. Provision the first org user through the existing IAM flow before initialization. Use an authenticated operator during rollout; do not enable enforcement and expect existing users' legacy role strings to grant access. Remove the bootstrap allowlist after rollout if operator recovery is managed another way. Disabling the feature restores the existing authorization factory; this is a deliberate configuration change across the cluster.

Use OpenFGA **1.10 or newer**. The HTTP adapter uses idempotent writes/deletes and batches of at most 100 tuples. The local development overlay is `deployment/docker-compose/compose.openfga.yml`. It includes PostgreSQL and runs OpenFGA database migrations before starting. Credentials in that overlay are local development values.

## Java platform declarations

```java
@PermissionNamespace("projects")
@ResourceTarget(type = "project")
@RequirePermission
public interface ProjectService {
    @RequirePermission("update")
    @ResourceTarget(idArgument = "entity.id")
    Future<Project> save(Project entity);

    @RequirePermission("repo.initialize")
    @ResourceTarget(idArgument = "projectId")
    Future<Project> retryRepoInitialization(String projectId);

    Future<Page<Project>> findAll(Pageable pageable);
}
```

These contracts require `projects.update`, `projects.repo.initialize`, and `projects.findAll`. Permission values are always relative to the service namespace; `projects.repo.initialize` inside the namespace `projects` would deliberately produce `projects.projects.repo.initialize`. An omitted permission value uses the method name. An omitted target ID means a scope-wide check. The target type inherits from the service unless the method overrides it.

`idArgument` explicitly names a caller-supplied parameter, optionally followed by property names. It is never inferred from argument position. Directory publication compiles its wire index after excluding injected Participant arguments. Gateway JSON extraction reads only as far as that argument, avoiding deserializing a later bulk payload. Named JSON arguments are supported for MCP. Text arguments support direct string IDs only.

Published management interfaces have class-level defaults. Project, application, and entity-definition CRUD methods override read/update/delete names and identify their exact targets. Other operations retain their declared service namespace and method-name permissions; a scope-wide grant does not turn into an inferred resource grant. Add an explicit target and an `AuthorizationResourceResolver` when introducing another organization resource type.

## UI administration

The portal has **Organization → Access control** and **Application → Access control**. Administrators pick users, create groups and roles, select permissions from the developer catalog, and assign roles to **ALL** or **EXACT** resources. Exact assignments currently accept the resource's ID. The server validates known platform resource ownership; app-defined resource IDs are namespaced by application and tenant.

For example, create a `Project editor` role containing `projects.update` and `projects.read`, then add an assignment with subject Alice, resource type `project`, selector EXACT, and the desired project ID. Alice can modify that project. Another project's permission object has a different ID, so the check denies it. Listing projects requires the separate scope-wide `projects.findAll` permission; the list is not automatically filtered by exact-resource grants.

The editor sends an `AuthorizationPolicy` document and `expectedRevision`. IDs, revisions, organization ownership, subject membership, and the permission catalog are checked on the server. A conflicting revision requires reload. Group members and direct subjects must be enabled identities from the policy's org/app/tenant scope. Delegating identities are not accepted as administrative grant subjects in this implementation.

Organization administrators automatically receive the current organization catalog. To delegate administration of one application's access, an org user needs scope-wide `access.manage` for the administration API and an exact `applications.access.manage` assignment on that application's ID. Server-side administration additionally verifies the app belongs to the caller's organization. Selecting another organization in a crafted request does not bypass this check.

Application administrators manage only their application. A tenant administrator manages only their tenant and only catalog permissions marked `tenantDelegable`. A root app policy can grant non-delegable permissions to app identities; a tenant policy cannot. The same capability may be used by multiple functions, but conflicting `tenantDelegable` declarations are rejected.

Customer applications can embed the shared editor with a scope derived from their authenticated session:

```vue
<AccessControlEditor :key="scopeKey" :scope="scope" :service="Kinotic.accessControl" />
```

The editor reads a scope-checked identity picker API; tenant administrators cannot list another tenant's identities. The portal remains an organization-only client. Its tenant selector is for organization administrators; customer-facing administrators use the shared component in their application.

## Decorator-first application code

```ts
@Publish('billing')
@PermissionNamespace('invoices')
@ResourceTarget({ type: 'invoice' })
@RequirePermission()
export class InvoiceService {
  @RequirePermission('approve', { label: 'Approve invoices', tenantDelegable: true })
  @ResourceTarget({ idArgument: 'invoiceId' })
  approve(invoiceId: string) { /* application logic */ }
}
```

Add `servicesPaths: ['./src/services']` to the project's existing Kinotic config. `kinotic sync` compiles service decorators and publishes app-scoped contracts through an organization-authorized API. It derives the service's zone from `@Zone` or `package.json`'s `kinotic.zone`; the server adds the authenticated organization's application zone prefix. String and option values must be literals. It publishes declared public instance methods; inherited/dynamically added methods require explicit declarations in the compiled service class. Contracts are upserted, not deleted by omission from a sync batch.

Administrators never edit these declarations. They use the catalog that sync publishes. Grants, groups, and roles stay as source policy documents in Elasticsearch. The gateway does not load those documents per request.

## Persistence integration

With the feature enabled, `OpenFgaAuthorizationServiceFactory` replaces the legacy persistence factory. Entity operations require `data.<methodName>` on resource type `entity_definition` with the published EntityDefinition ID. For example, `data.findAll`, `data.save`, and `data.deleteById` can be assigned to ALL entity definitions or one definition. Gateway and persistence checks both apply. Existing tenant filters and organization routing remain enforced; tenant participants cannot select another tenant or `*` through admin repository methods.

Entities, fields, and named queries may declare an additional permission:

```ts
@RequirePermission('invoices.amount.read', { resourceType: 'entity_definition', tenantDelegable: true })
amount!: number
```

The entity/query converter emits the same C3 permission decorator. Field access checks respect read field filters; writes conservatively require every protected field because EntityContext does not supply a changed-field set. Named queries use trusted ownership metadata and reject a descriptor that differs from the persisted entity. Authorization also rejects a client-supplied EntityContext participant that differs from the authenticated SecurityContext.

Legacy Policy decorators are rejected when OpenFGA is enabled. Migrate them explicitly; their restrictions are not silently discarded. This version controls entity-definition operations and declared fields. It does not implement per-row sharing, arbitrary resource-parent graphs, or embedded SpEL conditions. Existing entity tenancy still partitions row data.

## OpenFGA representation and request path

One org store contains organization permissions. Each application has an independent store and pinned immutable model ID; its root and tenant policies share that app's model. Updating one app's resource types does not update another app's schema.

The generated model has identity and group types, an `authorization_scope` type with allow/deny relations, and each declared resource type with a parent relation and an access permission:

```fga
model
  schema 1.1

type identity

type group
  relations
    define member: [identity]

type authorization_scope
  relations
    define allow: [identity, group#member]
    define deny: [identity, group#member]

type invoice
  relations
    define parent: [authorization_scope]
    define access: allow from parent but not deny from parent
```

Object IDs encode scope, resource ID, and capability. The ACL object ID additionally includes the resource type. IDs are deterministic; a check does not look up a randomly named role binding. Role provenance stays in the source policy. Projection compilation runs on a worker thread, with role permissions expanded once per publication. Overlapping assignments compile to one effective tuple, so removing one of them does not remove another assignment's grant.

Each Check specifies `storeId`, `authorization_model_id`, `HIGHER_CONSISTENCY`, the user's identity, relation `access`, the resource object, and up to four contextual parent tuples: tenant/app-wide and exact targets. Contextual parents are generated by the server. End users cannot supply them.

The gateway reads the current directory contract, validates the platform target's ownership where needed, reads model routing/revision, performs the OpenFGA Check, and reads the model revision again. Clients may omit a CRI version and use the current directory contract. An explicitly supplied version must match that contract. The existing event-bus routing ignores CRI versions: deploy only one active service contract per address; simultaneous versions with different permission contracts are not supported by this implementation. Coordinated gateway readiness during Java service upgrades also needs deployment validation. Missing metadata, transport errors, malformed responses, timeouts, pending publication, or a changed revision all deny dispatch. No allow-decision cache is used. The configurable deadline includes metadata/ownership work at the gateway; persistence adds its own checks. Model and contract reads currently use Elasticsearch per request. Latency and throughput must be measured before enabling this in production.

## Publication and recovery

Control-plane writes serialize with a cluster-wide lock per org/app. Caller authority is checked again after acquiring the lock. Publication increments the model revision and persists `pending=true` before changing any graph data. Candidate tuples are saved before writes so an interrupted publication can delete any partially written grants on retry. Desired tuples and source policies remain durable. Only a completed projection clears the fence.

A pending app store can be repaired by its owning organization administrator or a configured bootstrap operator. Pending organization access requires the bootstrap operator. Recovery rebuilds all policies sharing the model before clearing the fence. A failed save may already have persisted the source policy and incremented its revision: reload before retrying. Tenant administrators cannot repair the entire application model.

Source limits include 200 roles, 500 groups, 2000 assignments, 100 administrators, 2000 permission patterns, 10000 distinct policy subjects, 100000 projected tuples, and at most 97 resource types (plus the three framework types). Excessively long encoded OpenFGA tuple IDs are rejected before publication. These limits bound control-plane work, not the number of identities maintained in the authorization backend.

## Validation commands

```bash
./gradlew :kinotic-domain:test :kinotic-api-gateway:test :kinotic-idl:test :kinotic-persistence:compileJava :kinotic-management-api:compileJava

# Run the real graph tests against a disposable server with the local compose overlay:
OPENFGA_TEST_URL=http://localhost:8180 \
OPENFGA_TEST_TOKEN=kinotic-local-openfga \
./gradlew :kinotic-domain:test --tests '*OpenFgaIntegrationTest'

cd kinotic-js/workspace
bun install
bun run build
bun run type-check
cd ../../kinotic-frontend
pnpm install
# The frontend catalog normally consumes released packages. Link this branch's rebuilt packages for development.
pnpm link ../kinotic-js/workspace/packages/core ../kinotic-js/workspace/packages/idl ../kinotic-js/workspace/packages/persistence ../kinotic-js/workspace/packages/management-api
pnpm --filter kinotic-portal build
```

The integration fixture tests a real model, exact/group grants, deny precedence, revocation, idempotent recovery writes, tenant separation, and separate app stores. It is skipped unless `OPENFGA_TEST_URL` points to a disposable server. Unit tests cover overlapping grants, namespace wildcards, backend failure, deadlines, and the publication revision fence. Gateway tests verify that a denial never dispatches a service request.

This branch's initial implementation has not been performance-qualified. The implementation environment could not download build dependencies or run a live OpenFGA server. Java/TypeScript syntax checks are useful but do not replace compilation, integration tests, UI verification, or a measured latency budget. Complete those checks before rollout.
