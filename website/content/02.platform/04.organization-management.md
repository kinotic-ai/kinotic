## Overview

A Kinotic deployment hosts many customer organizations. Each org has its own users, applications, and (optionally) its own enterprise SSO configuration. This page describes how an org is created, who can log in to it, and how the OIDC plumbing is shared across orgs without leaking access between them.

System-level platform operators sign in to the system server, separately from everything described here; see [System Authentication](#system-authentication).

## Mental Model

Eight persistent entities carry the auth state, and one short-lived entity bridges each signup:

| Entity | Purpose | Lifecycle |
|---|---|---|
| `OrgSignupOidcConfiguration` | A registration the platform holds with a provider (GitHub) shown as a login/signup button to everyone. Belongs to no organization | Seeded by SQL migration |
| `ApplicationSocialOidcConfiguration` | A registration the platform holds with a social provider (Google, Microsoft) that any organization may offer at one of its applications' logins. Belongs to no organization | Seeded by SQL migration |
| `Organization` | A customer org | Created at the end of signup |
| `OrganizationOidcConfiguration` | A provider record (provider kind, account at the provider, clientId) owned by one organization for its own login; its client secret is held in the organization's scope of the secret storage, never on the record | Created by org admins |
| `ApplicationOidcConfiguration` | The same record made for the login of one of the organization's applications (`applicationId`) | Created by org admins |
| `Tenant` | A tenant of an application whose tenants its administrators manage: a customer of the application, whose users carry its id and whose sites, `<tenantId>--<applicationId>--<uiName>`, sign them in | Created by org admins, `TenantService` |
| `TenantOidcConfiguration` | The same record made for the login of one tenant of an application (`applicationId`, `tenantId`) | Created by org admins |
| `UserParticipantIdentity` | A person. An **account** carries neither `organizationId` nor `applicationId` and is unique by email; an application user carries both and belongs to that application alone | An account is created at signup, by invitation, or on a first SSO sign-in; application users by an admin, invitation, or `createUserOnSignIn` |
| `Membership` | An account's membership of one organization (`<identityId>:<organizationId>`), or of the platform for an operator (`<identityId>:system`), with its own `enabled` flag | Created at signup, by invitation, by `createUserOnSignIn`, or by an admin |
| `OidcBinding` | A provider identity bound to a user: `(oidcConfigId, subject)` → identity id, once among accounts and once per application among the application's users. With the optional password these are the user's sign-in methods | Created at signup, by invitation, by `createUserOnSignIn`, or by the user from the Profile page |
| `PendingSignUp` | Holds a signup in flight — the email-verification state for a local signup, or the verified identity for a social one, discriminated by `authType` | Short-lived; deleted once `/api/auth/org/signup/complete` or `/api/auth/org/signup/social/complete` succeeds |

A configuration is offered at the one scope its kind names. When the same Okta tenant serves both the org's own login and one of its applications', the org copies the configuration into the application's scope with `OidcConfigurationService.copy`; the copy is registered with the provider under its own callback URL and keeps its own copy of the client secret. An application offers the platform's Google and Microsoft registrations by naming their provider kinds in its `socialProviders`.

### Two distinct OIDC roles

| Role | Entity | Offered by | What the user sees |
|---|---|---|---|
| **Social sign-in** (org sign-up) | `OrgSignupOidcConfiguration` | Nothing — every enabled row is offered | A "Continue with GitHub" button on the login *and* signup pages |
| **Per-org SSO** (enterprise) | `OrganizationOidcConfiguration` | The org, at its own login, by creating the configuration | A "Sign in with <provider>" button on the organization's own login page, `/login/<organizationId>` |
| **Application SSO** | `ApplicationOidcConfiguration` | The org, at one of its applications' logins, by creating the configuration for that application | A "Continue with <name>" button on that application's own login page |
| **Application social sign-in** | `ApplicationSocialOidcConfiguration` | The application, by naming the provider kind in its `socialProviders` | A "Continue with Google/Microsoft" button on that application's own login page |
| **Tenant SSO** | `TenantOidcConfiguration` | The org, at the login of one tenant of one of its applications, by creating the configuration for that tenant | A "Continue with <name>" button on the tenant's own sites, before the application's buttons |

The roles are separate *subtypes* of `OidcConfiguration`, stored in one index under a `type` discriminator the way the kinds of `ParticipantIdentity` are, rather than one type with a flag, because the difference between them is ownership. Every lookup filters on the discriminator and every write is held to its kind's owner, so an org admin configuring SSO can never make it appear as a global button or name a platform secret, and a seeded platform registration can never affect an org's SSO settings.

## Org Creation

There are two entry points, both producing an `Organization` and an admin `ParticipantIdentity` scoped to it. The SPA's `/signup` page currently offers **GitHub only** (a hardcoded button — every Kinotic project is backed by a GitHub repository, so the founding user signs up with GitHub and installs the GitHub App right after). The email/password signup entry point remains fully mounted on the backend; its previous UI (`Signup.vue`) is kept in the tree unrouted until other methods return. Login is not restricted: invitees must be able to sign back in however they joined, so an organization's login page keeps every provider the organization offers plus a password form.

### Email/password signup (backend flow — not currently reachable from the SPA)

```text
1. User loads /signup, enters email + displayName
2. POST /api/auth/org/signup
3. SignUpService.initiateLocalSignUp:
   - rejects if a sign-up is already pending for this email, or if a ParticipantIdentity
     already exists for this email: a person founds one organization at most, and joins
     others by invitation
   - creates a PendingSignUp with a 24h verification token
   - EmailService sends the verification link (logs it instead when email is disabled)
4. User clicks /signup/verify?token=<verificationToken> in their inbox
5. /signup/verify form (VerifyEmail.vue) prompts for orgName + password + confirm
6. POST /api/auth/org/signup/complete  { token, orgName, orgDescription?, password }
7. SignUpService.completeLocalSignUp:
   - validates token, rejects if expired
   - creates Organization (auto-derived id from name)
   - creates the founder's account (UserParticipantIdentity with no organizationId or
     applicationId, enabled=true) with an IdentityCredential (bcrypt hash, separate index
     keyed by the account id)
   - creates the founder's Membership of the organization
   - links Organization.createdBy = account.id
   - deletes the PendingSignUp
8. The gateway establishes the browser session (204 + Set-Cookie); the frontend then calls
   userState.login() to open the realtime connection, authenticated by that session cookie.
```

Email verification is the security gate — no `Organization`, account or membership exists until the link is clicked. With `KINOTIC_EMAIL_ENABLED=false` (the local default) the verification URL is logged to the management server's console instead of sent; copy it into the browser to finish the flow.

### Social-IdP signup

```text
1. User loads /signup, clicks "Sign up with GitHub" (the page's only button today)
2. POST /api/auth/org/signup/social/start/github
3. OrganizationSignupHandler.handleSocialStart:
   - picks the OrgSignupOidcConfiguration whose provider key matches
     (oidcConfigurationService.findEnabledOrgSignupByProvider)
   - generates state/nonce/PKCE, stashes them on the session cookie
   - 302 to <authority>/authorize?...
4. User authenticates at the IdP
5. IdP returns to GET /api/auth/org/login/social/callback/<configId>, the one callback the
   registration is registered with; the flow's purpose, recorded at its start, routes it
6. OrganizationOidcCallbackHandler → OrganizationSignupHandler.complete:
   - validates state/nonce/PKCE, exchanges code for id_token + access_token
   - rejects if email_verified=false in the id_token
   - rejects with account_exists if an account is already bound to (configId, sub) or holds
     the verified email: a person founds one organization at most, and joins others by
     invitation; SignUpService checks again at completion, so two sign-ups of one identity in
     flight at once cannot both found an organization, and the organization is never created
     for an account that cannot be
   - creates a PendingSignUp with the verified subject, configId, email, displayName
   - 302 to /register?token=<verificationToken>
7. /register prompts for orgName (CompleteOrg.vue)
8. POST /api/auth/org/signup/social/complete  { token, orgName, orgDescription? }
9. SignUpService.completeOidcWithNewOrg:
   - validates the pending token
   - creates Organization
   - creates the founder's account (no organizationId or applicationId, enabled=true) with an
     OidcBinding of (configId, sub) to it
   - creates the founder's Membership of the organization
   - links Organization.createdBy
   - deletes the PendingSignUp
10. The gateway establishes the browser session (204 + Set-Cookie). CompleteOrg.vue then
    calls userState.login() to open the realtime connection, authenticated by that session
    cookie. No token travels in the URL.
11. CompleteOrg.vue shows a "Connect GitHub" step explaining that the next GitHub
    round-trip authorizes repository access (distinct from the sign-in, which only
    proved identity). Clicking "Continue to GitHub" calls
    githubAppInstallations.startInstall("/applications") and redirects the whole tab to
    the returned GitHub install URL. The App requests user authorization (OAuth) during
    installation, so GitHub returns to /github/install/callback — the App's first
    registered callback URL — with code, installation_id, and the state minted by
    startInstall. The callback runs completeInstall, which consumes the state, exchanges
    the code with the github-platform credential for the authorizing user's access
    token, and binds the installation only when GitHub's /user/installations reports
    that user can access it (see [Defense in Depth](/platform/defense-in-depth)). It
    then lands on /applications — project creation requires the install, so the new org
    arrives ready. If the install can't start, the page falls back to /applications
    directly.
```

The `PendingSignUp` is consumed once. The `?token=` in the redirect to `/register` is the short-lived `PendingSignUp` verification token, not an auth credential — the actual login is established by the session cookie set when the org-naming POST succeeds.

GitHub follows the same flow with one difference in step 6: GitHub is OAuth 2.0 only and issues no id_token, so its configuration row sets the endpoints explicitly instead of relying on discovery — `authorizationUri`/`tokenUri` drive the code flow, `userInfoUri` supplies `sub` and the display name, and `userEmailsUri` supplies the email plus its `verified` flag (primary address preferred). Any curated row that sets these fields takes this path; nothing about it is GitHub-specific in code, and only a curated row can set them. Issuer, audience, and nonce validation don't apply (there is no token to carry them); the state match and the direct TLS code exchange are the security boundary.

## User Login

A login is addressed to an organization. An account may be a member of any number of organizations, each a `Membership` of its own, so nothing about the person alone says where they are signing in; the organization's id, the slug of its hostnames (see [Applications and Projects](/apps/application-structure/applications-and-projects#applications)), is what every login route and page is addressed by. The portal has two login pages:

- `/login`, the landing page, for someone whose organization is not yet known: the platform's social buttons, which sign in without naming an organization when the identity belongs to exactly one and otherwise offer the ones it belongs to; an organization field that leads to that organization's page (prefilled with the organization this browser last signed in to); and a "Don't know your organization?" link that emails the person the organizations their address belongs to.
- `/login/<organizationId>`, the organization's page (`OrganizationLoginPage.vue`), which offers exactly what that organization's login supports: one button per configuration `GET /api/auth/org/login/<organizationId>/providers` lists — the platform's org sign-up registrations (GitHub) followed by the organization's own `OrganizationOidcConfiguration`s — and an email + password form. The organization's own host, `<organizationId>.<sitesDomain>`, redirects here.

No route asks about an email first: the page offers every method up front, and the password login answers a generic `401`, so nothing tells whether an email has an account anywhere. What the page does disclose, to anyone who knows an organization's id, is that the organization exists and the names and provider kinds of the configurations its login offers, as any SSO login page does; the id is already public as the organization's hostname, and the configurations are the buttons the page shows. A signed-in member of several organizations switches between them without signing in again: the account menu's **Organizations** list posts `POST /api/auth/org/switch { organizationId }`, which re-establishes the session for the chosen membership and reloads the portal.

### Password

The form posts email + password to the organization's login route, which verifies the credential and **establishes a browser session** — there is no client-held token. The `fetch` uses `credentials: 'include'` so the gateway's `Set-Cookie` is stored even cross-origin:

```text
1. POST /api/auth/org/login/<organizationId> { email, password }   (credentials: 'include')
2. OrganizationLoginHandler.handleLogin → AuthEndpointSupport.handlePasswordLogin:
   - LocalAuthenticationService.authenticateLocal(email, password, null, null)
       finds the account with that email (an application user with the same email is
       another row and never signs in here), requires it enabled, loads its
       IdentityCredential and verifies the bcrypt hash; an account with no password
       fails here
   - ParticipantIdentityService.resolveParticipant(account.id, organizationId, null)
       requires the account's enabled Membership of that organization and makes the
       OrganizationParticipant from the two
   - on success: establishSession(ctx, participant) puts it on the Vert.x session
                 (regenerating the session id), then 204 + Set-Cookie
   - on any failure: 401 "Invalid credentials"
                     (deliberately generic — covers unknown email, wrong password,
                      no password, disabled account or membership, not a member)
3. OrganizationLoginPage.vue calls userState.login() → Kinotic.connect().
   The default resolution supplies no auth headers in a browser, so the
   WebSocket upgrade is authenticated by the session cookie set in step 2.
```

The SPA never exchanges the password for a token and never sends raw passwords over the WebSocket. Non-UI clients (CLI, automation) do not use this path — they authenticate directly at the upgrade instead; the table in "The WebSocket upgrade" below covers what each client type presents.

### A provider the organization offers

Each button on the organization's page is a form posting to the organization's start route for that configuration. The route also answers `GET`, so a link — from a bookmark, or from the organization's own tile in its provider's application launcher — starts the same flow:

```text
1. POST|GET /api/auth/org/login/<organizationId>/start/<configId>?referer=<spa-path>
   - the router guard bounced an unauthenticated navigation to /login?referer=<spa-path>,
     and the login pages forward it here; a provider sign-in leaves the SPA, so the path
     cannot be kept client side the way the password path keeps it
2. OrganizationLoginHandler.handleStart:
   - an enabled OrgSignupOidcConfiguration under that id, which every organization's
     login offers; otherwise the organization's own configuration under it
     (oidcConfigurationService.findOffered(configId, organizationId, null)); 400 for
     anything else
   - stashes the organization on the flow session, with the referer when it names a
     path within the SPA, then state/nonce/PKCE as for signup, and 302 to the IdP
   - the completed login is bound to the page that started it, or to the portal when a
     GET link, which names no page, started it
3. IdP returns to the callback registered for the configuration:
     GET /api/auth/org/login/social/callback/<configId>   an org sign-up registration
     GET /api/auth/org/login/sso/callback/<configId>      the organization's own configuration
4. OrganizationLoginHandler → AuthEndpointSupport.completeOidcLogin:
   - validates state/nonce, exchanges code, validates id_token (sub + email_verified)
   - looks up the account bound to (configId, sub) (ParticipantIdentityService.
     findByOidcIdentity) and its Membership of the stashed organization
   - no account: for the organization's own configuration with createUserOnSignIn, an
                 account is created from the verified email and name, bound to the
                 identity (account_exists when the email already has an account — only
                 its holder may connect a provider to it); otherwise 302
                 /login?error=no_account
   - no membership: with createUserOnSignIn the account joins the organization and signs
                    in; otherwise 302 /login?error=no_account
   - a disabled account or membership: 302 /login?error=account_disabled
   - otherwise: establishSession(ctx, participant), then redirectSuccess → 302 to the
       stored referer, or the SPA root when the flow stored none, with Set-Cookie.
       No token travels in the URL.
5. The SPA loads with the session cookie set; userState.login() opens the realtime
   connection, authenticated by that cookie.
```

### Social button on the landing page

The landing page's buttons are populated from `GET /api/auth/org/login/providers`, which lists the unique provider keys present in the org sign-up configs (the invite-hint UI on `MembersPage` reads the same endpoint). A sign-in there names no organization, so its callback finds the one organization the identity is a member of:

```text
1. POST /api/auth/org/login/social/start/github?referer=<spa-path>
2. OrganizationLoginHandler.handleSocialStart:
   - finds the OrgSignupOidcConfiguration with provider="github"
     (oidcConfigurationService.findEnabledOrgSignupByProvider)
   - same flow-session setup as above, with no organization stashed, then 302 to the IdP
3. IdP returns to GET /api/auth/org/login/social/callback/<configId>
4. OrganizationLoginHandler.handleSocialCallback → completeOidcLogin:
   - finds the account bound to (configId, sub) and its enabled Memberships
     (MembershipService.findMemberships)
   - exactly one: signs in to that organization as above
   - no account, or no enabled membership: 302 /login?error=no_account
   - several: 302 /login?error=multiple_organizations&organizations=<ids> — the
     account has proven who it is, so the landing page offers those organizations
     to choose from, and the person signs in at the chosen one's own page
```

### Finding one's organizations

`POST /api/auth/org/login/find { email }` emails the address every organization its account holds an enabled membership of, each with a link to that organization's login page (`OrganizationService.sendMembershipsEmail`). The route always answers `204` and the email is sent whether or not the address belongs to any organization — one that belongs to none says so — so the request reveals nothing about the address. With `KINOTIC_EMAIL_ENABLED=false` the links are logged to the management server's console instead of sent.

### Platform operators (SYSTEM scope)

A platform operator is an account holding the platform membership (`Membership` with no `organizationId`, id `<identityId>:system`). They sign in through a separate, password-only route used by the system console (there is no signup, SSO, or social path for SYSTEM scope):

```text
1. POST /api/auth/system/login { email, password }   (credentials: 'include')
2. SystemLoginHandler.handleLogin → AuthEndpointSupport.handlePasswordLogin:
   - LocalAuthenticationService.authenticateLocal(email, password, null, null)
       verifies the account's password, then resolveParticipant(account.id, null, null)
       requires its enabled platform membership — an account without one, however
       many organizations it belongs to, can never authenticate here
   - success/failure behave exactly like the org password branch:
     204 + Set-Cookie, or a generic 401
```

The session established here is the same browser-session mechanism as every other login path; `/api/auth/me` and `/api/auth/logout` apply unchanged.

The console lists them at **Members → Users**, read-only, from `SystemMemberService.findUsers` in the system zone, which lists the accounts holding the platform membership. Operators are created outside the console — by the migration fixtures, or by the identity provider once SYSTEM scope is behind Entra — so the page reports who holds access rather than granting it.

### The WebSocket upgrade (the final step in every path)

Authentication happens at the WebSocket upgrade (handshake), not in a STOMP CONNECT frame. How the upgrade is authenticated depends on the client:

| Client | Upgrade credentials |
|---|---|
| Browser SPA | Session cookie established by the REST login; the default credential resolution supplies no headers |
| Node client, credentials | `clientId`, `clientSecret`, plus `organizationId` / `applicationId` scope headers (via `BasicCredentialsResolver` or the `KINOTIC_CLIENT_*` environment variables) |
| Node client, Bearer token | `Authorization: Bearer <jwt>` (via `BearerCredentialsResolver`); a Kinotic JWT carries the `organizationId` / `applicationId` claims |

The browser SPA never holds a JWT — its login establishes a session cookie and that cookie authenticates the upgrade. The Bearer path is for non-browser clients: the CLI obtains an access token through the OAuth device-code grant at `POST /api/auth/oauth/token`, which mints a Kinotic JWT carrying `sub` / `email` / `organizationId` / `applicationId`. For that path the management server validates the JWT signature against its signing keys and creates the `Session`. Every path admits only the server's own kind of participant: a credential that proves an identity of another scope fails as invalid (see [System Security](/platform/system-security#authentication-methods)). The CLI persists a rotating refresh token to mint fresh access tokens before each connect.

## Provider-Specific Quirks

OIDC is a standard, but providers diverge on a few details. The validation helpers in `OAuth2Util` (`isIssuerValid`, `isEmailVerified`) handle these declaratively — the provider key on `OidcConfiguration` selects the right behaviour. No provider needs handler-level branching: a row either has an `authority` for OIDC discovery — derived from the organization's `providerAccount` for an organization's row, seeded for a curated one — or, for a curated row only, sets `authorizationUri`/`tokenUri`/`userInfoUri`/`userEmailsUri`/`scopes` explicitly, and every handler consumes the same claims shape either way.

| Provider key | `iss` shape | `email_verified` claim | Other notes |
|---|---|---|---|
| `github` | No id_token — identity is fetched from the row's `userInfoUri` with the exchanged access token, so issuer/nonce validation doesn't apply | Synthesized from the row's `userEmailsUri` — the primary verified address is preferred, any verified address accepted | OAuth 2.0 only, so the row sets every endpoint explicitly. `sub` is the numeric GitHub account id. Uses the kinotic-ai GitHub App's user-authorization OAuth credential — the same credential that verifies installation ownership when an org links GitHub, so the row must never point at a different OAuth client. The app needs the "Email addresses: read-only" permission, and its scope param is ignored (GitHub App permissions govern access) |
| `google` | Fixed `https://accounts.google.com` | Emitted as boolean — required `true` to accept | `sub` is per-OAuth-client pairwise (different Kinotic deployments see different `sub`s for the same person — fine since we key on `(sub, configId)`) |
| `azure-ad` (single tenant) | Fixed `https://login.microsoftonline.com/<tenant-id>/v2.0` | Not emitted — email-presence is treated as verified (Entra verifies via tenant domain ownership) | Used by per-org SSO configs that pin to a specific Entra tenant |
| `azure-ad` (multi-tenant `/common` or `/organizations`) | Per-user — substitutes user's home tenant id; we re-validate by extracting `tid` from the same signed JWT | Same as single-tenant — not emitted, presence trusted | Discovery doc returns a literal `{tenantid}` placeholder; we set `validateIssuer=false` and clear `jwtOptions.issuer` for this case so Vert.x's strict comparison doesn't reject |
| `apple` | Fixed `https://appleid.apple.com` | Not emitted — presence trusted | Email is **only present on first sign-in**; later tokens omit it. Returning users are recognised by stable `sub`. May be a `…@privaterelay.appleid.com` private-relay address — still verified |
| `okta` | Fixed, `https://<okta domain>`, derived from the organization's Okta domain | Emitted as boolean — required `true` | Discovery + standard validation |
| `keycloak`, `auth0`, `salesforce`, `amazon-cognito`, `oidc` (generic) | Fixed (issuer URL of the realm/tenant) | Emitted as boolean — required `true` | Discovery + standard validation; not yet offered to organizations, since no issuer template exists for them |

`isEmailVerified` and `isIssuerValid` are the only places these differences live in code. Adding a curated provider doesn't require code changes — an OIDC-compliant provider seeds a row with an `authority`, and a plain-OAuth2 provider seeds a row with explicit endpoint fields; only providers with non-standard claim quirks (Apple's first-login-only email, Microsoft's `/common` issuer template) need to be classified explicitly in those helpers. Offering a kind to organizations is one line on `OidcProviderKind`: its issuer template and the pattern the organization's account must match.

## Per-Org SSO Configuration

The data model already supports per-org SSO: an `OrganizationOidcConfiguration` is offered at the org's own login page, `/login/<organizationId>`, by existing. The piece that's not built yet is the **admin UI** for an org admin to create those rows.

For now, per-org SSO can be wired manually:

1. Create the `OrganizationOidcConfiguration` as the organization through `OidcConfigurationService.save(configuration, clientSecret)`, naming the provider kind (`azure-ad`, `okta` or `google`) and the organization's `providerAccount` at it; the authority is derived from the kind's template, so no URL is given. A null secret makes a public client (`confidentialClient` false); a secret is held in the organization's own scope of the secret storage — the row itself never names one. Set `createUserOnSignIn` to let a person the provider verifies join the organization on their first sign-in — their account is created from the verified email if they have none, and otherwise the account bound to the identity gains a membership; off, members are invited. With it on, the provider decides who is a member: a member who was removed joins again on their next sign-in for as long as the provider verifies them, so to keep someone out, disable their membership or remove them at the provider.
2. To offer the same provider at one of the org's applications, copy it there with `OidcConfigurationService.copy(configurationId, applicationId)`, which makes an `ApplicationOidcConfiguration` with a callback URL of its own, `<appServerApiBaseUrl of the application>/api/auth/app/login/oidc/callback/<copyId>`, to register with the provider as well.
3. Add the redirect URI `<kinotic.managementServer.apiBaseUrl>/api/auth/org/login/sso/callback/<configId>` to the IdP app registration. It is the only one the configuration needs: a login, an invitation accepted through the provider, and a member connecting the provider to their account from the Profile page all return to it, and the flow's purpose, recorded on the session when it starts, says which it is. For a same-origin deploy that base is the portal's own origin; for a split-origin deploy (SPA on Static Web Apps, backend on AKS) it is the backend's hostname, so the IdP returns the browser to the management server, not the SPA.

A user who logs in via this path lands at the `/api/auth/org/login/sso/callback/:configId` handler — the IdP doesn't care that the configId is org-scoped instead of platform. The provider's application launcher can link straight to `<kinotic.managementServer.apiBaseUrl>/api/auth/org/login/<organizationId>/start/<configId>`, which starts the same flow from a plain `GET`.

## System Authentication

System-level operators are accounts holding the platform membership; they sign in to the system server with an email and password, `POST /api/auth/system/login`, and the plan is to move it to Microsoft Entra, separate from the routes documented above. The curated social providers are intentionally limited to end-user self-service signup and grant org-scoped access only, so no organization route can produce a `SYSTEM`-scoped session.

## Endpoint Reference

Each handler is a component of the module that serves it, so a server mounts the routes of the modules it loads, on its own gateway port (org `58503`, system `58504`, app `58505` by default):

| Handler | Module | Management server | System server | App server |
|---|---|---|---|---|
| `OrganizationOidcCallbackHandler`, `OrganizationLoginHandler`, `OrganizationSignupHandler`, `AccountSignInMethodHandler`, `InviteHandler`, `DeviceAuthorizationHandler`, `GitHubWebhookHandler` | `kinotic-server-management` | ✓ | | |
| `SystemLoginHandler` | `kinotic-server-system` | | ✓ | |
| `ApplicationLoginHandler`, `ApplicationSocialLoginHandler` | `kinotic-server-app` | | | ✓ |
| `SessionEndpointHandler`, `OAuthServerHandler` | `kinotic-domain` | ✓ | ✓ | ✓ |
| `McpJsonRpcHandler` | `kinotic-management-api` | ✓ | ✓ | |

The app server serves every application at an API host of its own, `<organizationId>--<applicationId>` under `kinotic.appServer.apiBaseUrl` (see [Configuration](/platform/configuration#application-api-hosts)). Its login and OAuth routes act for the application whose host the request is addressed to and answer `404` on any other host, and that host is the application's OAuth issuer. The one exception is a sign-in through a platform social registration (`ApplicationSocialOidcConfiguration`): a provider returns the browser only to a redirect URI registered in advance, and the registration is shared by every application that offers it, so its `authorize` and `callback` routes are served at `kinotic.appServer.apiBaseUrl` itself, the shared host, and the verified sign-in is handed to the application's own host under a single-use code (`SocialLoginHandoffService`, an Ignite cache with a one-minute TTL) where the session is established.

CORS for the server's UI origin is applied at the router root. A Vert.x `SessionHandler` covers every `/api/*` route (and the STOMP WebSocket path), so the same session cookie carries the OIDC roundtrip state and the post-login identity; the cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, with a configurable timeout (`kinotic.api-gateway.session-timeout`).

Routes are namespaced under `/api/auth/...`. Organization login and signup are the SPA's paths; the application-login, OAuth, and invite routes are listed for completeness.

| Method | Path | Owner | Purpose |
|---|---|---|---|
| `GET`  | `/api/auth/org/login/providers` | `OrganizationLoginHandler` | Unique social provider keys for the landing page's button row |
| `POST` | `/api/auth/org/login/find` | `OrganizationLoginHandler` | `{email}`; emails the address its organizations' login links; always `204` |
| `POST` | `/api/auth/org/login/social/start/:provider` | `OrganizationLoginHandler` | Begin a social-button login from the landing page, addressed to no organization; redirects to the IdP |
| `GET`  | `/api/auth/org/login/social/callback/:configId` | `OrganizationOidcCallbackHandler` | The one callback a platform registration is registered with: a login signs in to the stashed organization, or the one organization the identity is a member of; a sign-up, an invitation or a connect is completed by its own handler, as the flow's recorded purpose says |
| `GET`  | `/api/auth/org/login/sso/callback/:configId` | `OrganizationOidcCallbackHandler` | The one callback an organization's own configuration is registered with: a login establishes the session, an invitation or a connect is completed by its own handler |
| `GET`  | `/api/auth/org/login/:orgId/providers` | `OrganizationLoginHandler` | Enabled configurations the organization's login offers, `[{id, name, provider}]`; `404` for an unknown organization |
| `POST` | `/api/auth/org/login/:orgId` | `OrganizationLoginHandler` | Email + password, scoped to the organization; on success establishes the browser session (204 + Set-Cookie) |
| `POST`, `GET` | `/api/auth/org/login/:orgId/start/:configId` | `OrganizationLoginHandler` | Begin a sign-in to the organization through a configuration its login offers; redirects to the IdP; `400` for one not offered |
| `POST` | `/api/auth/org/switch` | `OrganizationLoginHandler` | `{organizationId}`; re-establishes the signed-in account's session for another of its enabled memberships (204); `401` without a login, `403` for an organization it is not a member of |
| `POST` | `/api/auth/account/methods/start/:configurationId` | `AccountSignInMethodHandler` | Connect a configuration to the signed-in account: a platform registration, or an organization's own configuration when the account may sign in there (`403` otherwise); redirects to the IdP, whose callback binds the identity and 302s to `/account/profile?connected=<name>`, or `?error=identity_in_use` when it is bound to another account |
| `POST` | `/api/auth/org/signup` | `OrganizationSignupHandler` | Submit email + displayName; sends verification email |
| `POST` | `/api/auth/org/signup/complete` | `OrganizationSignupHandler` | Verify token + orgName + password; creates Organization, the founder's account and membership; establishes session |
| `POST` | `/api/auth/org/signup/social/start/:provider` | `OrganizationSignupHandler` | Begin social-IdP signup; redirects to the IdP |
| `POST` | `/api/auth/org/signup/social/complete` | `OrganizationSignupHandler` | Consume PendingSignUp; create Org, the founder's account bound to the GitHub identity, and membership; establishes session |
| `POST` | `/api/auth/system/login` | `SystemLoginHandler` | System operator email + password; establishes session |
| `GET`  | `/api/auth/app/login/providers[?tenantId]` | `ApplicationLoginHandler` | Enabled configurations the application's login offers, `[{id, name, provider}]`, or the tenant's login from one of the tenant's sites or when `tenantId` names one; `404` for a tenant the application does not have |
| `POST` | `/api/auth/app/login` | `ApplicationLoginHandler` | `{email, password[, tenantId]}`, scoped to the application, or to the tenant from one of the tenant's sites or when `tenantId` names one; establishes session; `403` from a page that is not one of the application's UIs or is a site of another tenant |
| `POST` | `/api/auth/app/login/oidc/start/:configId[?tenantId]` | `ApplicationLoginHandler` | Begin a sign-in through a configuration the login offers; `{redirect}` naming the IdP's authorization URL, or the shared host's `authorize` URL for a platform social registration; `400` for one not offered, `403` from a page that is not one of the application's UIs |
| `GET`  | `/api/auth/app/login/oidc/callback/:configId` | `ApplicationLoginHandler` | App IdP returns here; establishes session for the scope the flow started for, 302 to the page that started the login |
| `GET`  | `/api/auth/app/login/social/authorize` | `ApplicationSocialLoginHandler` | Shared host: begins the provider round-trip for `organizationId`, `applicationId`, `configurationId`, `tenantId` when the sign-in is to a tenant, and the page at `origin`, which must be one of the application's UIs; redirects to the IdP |
| `GET`  | `/api/auth/app/login/social/callback/:configId` | `ApplicationSocialLoginHandler` | Shared host: the IdP returns here; verifies the identity, 302 to the application's host with a single-use code |
| `GET`  | `/api/auth/app/login/social/complete/:code` | `ApplicationSocialLoginHandler` | Consumes the code; establishes session, 302 to the page that started the login; `handoff_invalid` for a spent, expired or foreign code |
| `GET` | `/.well-known/oauth-authorization-server` | `OAuthServerHandler` | RFC 8414 authorization-server metadata |
| `GET` | `/.well-known/oauth-protected-resource[/mcp]` | `McpJsonRpcHandler` | RFC 9728 resource metadata for `/mcp` |
| `POST` | `/mcp` | `McpJsonRpcHandler` | MCP JSON-RPC endpoint (see [MCP Tools](/platform/mcp-tools)) |
| `GET` | `/api/auth/oauth/authorize` | `OAuthServerHandler` | PKCE authorization-code flow; redirects to the `/oauth/consent` page on the server's UI, on the app server the application's primary UI (`400` until one is chosen) |
| `GET` | `/api/auth/oauth/request/:requestId` | `OAuthServerHandler` | The request awaiting consent, for the consent page's signed-in user |
| `POST` | `/api/auth/oauth/approve` | `OAuthServerHandler` | Approves the request as the consent page's signed-in user; answers the client redirect URL carrying the code |
| `POST` | `/api/auth/oauth/deny` | `OAuthServerHandler` | Denies the request; answers the client redirect URL carrying `error=access_denied` |
| `POST` | `/api/auth/oauth/device_authorization` | `DeviceAuthorizationHandler` | RFC 8628 device grant — issue device/user codes; requires the CLI's `client_id` |
| `POST` | `/api/auth/oauth/device/approve` | `DeviceAuthorizationHandler` | Approves the user code the `/device` page's signed-in user confirmed |
| `POST` | `/api/auth/oauth/token` | `OAuthServerHandler` | Token endpoint: `authorization_code` and `refresh_token` grants, plus every extension grant a module publishes — on the management server `DeviceAuthorizationHandler`'s device-code grant |
| `GET`  | `/api/auth/invite/details` | `InviteHandler` | Invitation details, the organization's live provider list (empty for an application invitation), `accountExists` — whether the invited email already has an account — and `accountHasPassword`, without which that account joins through a provider it is bound to |
| `POST` | `/api/auth/invite/accept` | `InviteHandler` | Accept with a password: sets it on the new account or user, or, when the invited email already has an account, must be that account's password (`401` otherwise), and the account and its membership of the organization must be enabled (`403` otherwise); an organization member's session is established, while an application member signs in at the application |
| `POST` | `/api/auth/invite/oidc/start/:configId` | `InviteHandler` | Accept an organization invitation through a configuration the organization's login offers; redirects to the IdP, whose callback completes the acceptance: the identity's verified email must be the invited one; it joins the account it is bound to, or creates and binds one, and establishes an organization member's session; `account_exists` when the email's account has no binding for the identity, so the holder accepts with the password instead; `account_disabled` when the account or its membership is disabled. An application invitation is accepted with a password |
| `GET`  | `/api/auth/me` | `SessionEndpointHandler` | `204` if the session cookie holds a login for the calling page, else `401` |
| `POST` | `/api/auth/logout` | `SessionEndpointHandler` | Ends the calling page's login; the session ends once no page's login or sign-in in progress remains |
| `POST` | `/api/github/webhook` | `GitHubWebhookHandler` | GitHub App webhook, verified against the App's webhook secret |

For the underlying architectural rationale (scope isolation, credential separation, the two kinds of `OidcConfiguration`), see [System Security](/platform/system-security).
