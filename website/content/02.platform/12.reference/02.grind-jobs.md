## Overview

Grind (the `kinotic-grind` module) is the platform's job framework: multi-step work such as a project deployment or a provisioning pipeline, expressed as a **job** of **tasks** that share a scope. Its core idea is declarative state injection — instead of threading an ever-growing context object through every step, each task declares what it consumes, injected from the job scope, and what it produces, stored back under a `Store`. Every run is recorded, resumable after a failure, and observable as a live event stream.

## Defining a job

A `JobDefinition` is built fluently. Tasks execute in the order they are added, and each task's result is kept according to the `Store` the task declares:

```java
JobDefinition job = JobDefinition.create("Deploy project")
        .name("project-deploy").version("1")
        .input(project)                       // seeds the scope before the first task
        .task(Tasks.fromCallable("Resolve deploy target", new Callable<DeployTarget>() {

            @Autowired
            private Project project;          // injected from the job scope

            @Override
            public DeployTarget call() {
                return resolveTarget(project);
            }
        }).store(Store.state("deployTarget")))
        .task(Tasks.fromCallable("Sync project source", new Callable<String>() {

            @Autowired
            private DeployTarget target;      // stored by the previous task

            @Override
            public String call() {
                return syncSource(target);
            }
        }));
```

`name` and `version` identify the job across runs and are required to run it. `input(...)` stores values in the scope as beans, so the first task's dependencies resolve the same way as any other.

Definitions nest: `jobDefinition(...)` adds a whole `JobDefinition` as one task of another. A nested definition declares a `JobScope` — `CHILD` (the default) gives it a scope of its own that is destroyed when it finishes, while `PARENT` lets it store directly into its parent's scope. Passing `parallel = true` to `JobDefinition.create` makes the definition's tasks execute concurrently; the first failure cancels the in-flight siblings.

### Task factories

The `Tasks` class adapts plain functional types into tasks. Each factory takes what every task needs, its description and its work; everything else is set with the fluent methods of the returned `Task`. A `Task` is immutable: each fluent method returns a copy, so one instance can be added to several definitions, or serve as a step and as another step's reload task, without either seeing the other's settings. The instance-taking factories inject the given instance's `@Autowired` and `@Value` members against the job scope before invoking it:

- `Tasks.fromCallable(description, callable)` — the result is the callable's return value
- `Tasks.fromSupplier(description, supplier)` / `Tasks.fromRunnable(description, runnable)`
- `Tasks.fromValue(description, value)` — a constant
- `Tasks.fromClass(description, callableClass)` — a new instance is constructed on each execution, with full injection against the scope
- `Tasks.noop(description)` — does nothing
- `Tasks.transformResult(task, transformer)` — maps another task's result

### Task classes

A whole job can be one annotated class, compiled with `JobDefinition.fromTasks(...)`. Each `@Task` method is a task, executed in `order`; parameters are injected from the scope by type, and the return value is stored back under the method's `store` mode with a name derived from the returned type:

```java
public class ProvisioningTasks {

    @Task(order = 1)
    public ClusterSpec resolveCluster(Project project) { ... }   // stored as "clusterSpec"

    @Task(order = 2, store = StoreType.STATE)
    public TopicPlan planTopics(ClusterSpec cluster) { ... }     // durable decision

}

JobDefinition job = JobDefinition.fromTasks(ProvisioningTasks.class)
                                 .name("provision-kafka").version("1");
```

The class is instantiated once per run with constructor arguments resolved against the application context — it is never a Spring bean itself. Compilation fails fast on duplicate orders and on a task consuming a type that only a later task produces.

## The job scope

`JobContext` is the scope tasks share. Values stored by earlier tasks are available to later ones: beans by type through `@Autowired` injection or `getBean(Class)`, named values through `@Value("${name}")` or `getProperty(String)`. Lookups fall through parent scopes down to the application's own beans and configuration, so a task can inject platform services and job-produced values through the same mechanism.

## Storing results

How a value behaves on resume and whether watchers of the run may see it are independent choices, declared together on an immutable `Store`:

```java
.task(task)                                // keep nothing
.task(task.store(Store.none().wire()))     // keep nothing, publish to watchers
.task(task.store(Store.result("widget")))  // scope value, re-derived on resume
.task(task.store(Store.result("widget").wire()))
.task(task.store(Store.state("decision"))) // durable, replayed on resume
.task(task.store(Store.state("decision").wire()))
```

The `StoreType` axis answers *what survives a resume*:

- **`NONE`** — the value is discarded. On resume a completed task is skipped.
- **`RESULT`** — the value is stored in the scope but not persisted. On resume the task re-executes to regenerate it — or its declared reload task runs instead: `Store.result("workload").reload(reloadTask)` pairs a task that creates external state with the task that reloads it from its source of truth, so the creation is never repeated.
- **`STATE`** — the value is stored in the scope and serialized into the run's `TaskRecord`. On resume it is replayed from the record without executing. The value must survive a JSON round trip: a plain class or record with concrete field types. Generic values such as `List`, `Map`, and `Optional` are rejected at completion, because type erasure would make the record unrestorable.

The `wire()` axis answers *who may see it*: a wired value is serialized as JSON onto the run's `TaskCompletedEvent` and kept on the task's record as its `wireValue`, so watchers — including remote ones, which never receive live objects — can read it while the run executes and after it has finished. The `StoreType` decides what a resume replays; `wire()` decides what watchers see. Durable state stays private unless it opts in — the `stateValue` a resume replays never leaves the server — a result store can publish without being durable, and `Store.none().wire()` publishes a value that exists only for observers. Wire values only have to serialize, never deserialize, so the `STATE` restrictions on generics do not apply to them.

Use `STATE` for decisions and allocations the rest of the run depends on; use `RESULT` for lookups whose source of truth can answer again; add `wire()` for a result the run's remote watchers consume as data. What a console shows for a task is its view, declared separately (see [Presenting a task](#presenting-a-task)).

## Dynamic tasks

Structure can be decided at runtime: a task may return another `Task`, or a whole `JobDefinition`, instead of a value. The returned work is discovered, reported to watchers as a `TasksDiscoveredEvent` flagged `dynamic` and carrying the producing task's path, and executed in place under that path. A dynamic `Task` that declares no `Store` of its own keeps its value as the producing task's `Store` declares; one that declares its own keeps it that way.

## Asynchronous results and Vert.x

A task may return its value directly, or asynchronously as a `CompletionStage`, a Vert.x `Future`, or a `Publisher` (whose last emission is the value) — the framework awaits it before storing.

Prefer the Vert.x `Future`: it is the platform's async type, and every platform repository and service already returns one. Return a `CompletionStage` only when a library offers nothing else — the Elasticsearch and Azure clients, for instance.

Every run executes on its own Vert.x virtual-thread context, and each parallel child gets its own. Inside a task, `Vertx.currentContext()` resolves, context-locals such as the platform `SecurityContext` participant work, blocking is permitted, and Vert.x futures can be awaited in place:

```java
String answer = vertx.timer(20).map(v -> "ticked").await();   // parks the virtual thread
```

**Never block on a future with `CompletableFuture.get()` or `join()` inside a task body.** Return the asynchronous value and let the framework await it, or await a Vert.x future in place with `.await()`. Both of those suspend the run's context so its queued work keeps flowing; `get()` and `join()` park the thread while it still holds the context, which stalls everything queued behind the task:

```java
@Task(order = 2)
public DeployTarget load(DeployTargetRepository repository, Project project) {
    return repository.findById(project.getId())
                     .toCompletionStage().toCompletableFuture().join();   // deadlocks the run
}

@Task(order = 2)
public Future<DeployTarget> load(DeployTargetRepository repository, Project project) {
    return repository.findById(project.getId());                          // the framework awaits it
}

@Task(order = 2)
public DeployTarget load(DeployTargetRepository repository, Project project) {
    return repository.findById(project.getId()).await();                  // or await it in place
}
```

How bad the stall is depends on where the future came from. A future bound to the run's context — anything a platform repository or service hands back — delivers its completion *through* that context, so `get()` waits on a completion queued behind itself and the run hangs permanently. A raw library future completes on its own thread, so the task does eventually proceed, but everything queued on the run's context — record writes, event delivery — waits until it does.

## Running and watching

`JobService` executes definitions:

```java
JobRunHandle handle = jobService.run(job, JobOwner.ofApplication(orgId, appId, projectId));
```

`JobOwner` records which tier the run executes on behalf of — `system()`, `ofOrganization(...)`, or `ofApplication(...)` — and, for an organization or application owner, the project the run served, so runs can be filtered by owner down to one project.

The handle pairs the persistent run's id with the run's event stream. **Execution is lazy**: nothing runs until the first subscriber attaches to `handle.getEvents()`, the job executes exactly once no matter how many subscribers attach, and every subscriber replays the full event history from the beginning. `handle.completion()` returns a future for the terminal outcome (subscribing, and so starting the run, if nothing else has), and `handle.cancel()` aborts the run, recording it as `CANCELLED`.

The stream emits the sealed `JobRunEvent` family, each carrying the task's `taskPath` — its `/`-separated position in the run's task tree:

- **`TasksDiscoveredEvent`** — the task tree, at the start of the run and again as dynamic tasks appear; its `dynamic` flag says which, so watchers can mark the producing task the moment it reveals a subtree
- **`TaskStartedEvent`** — a task began executing, carrying the view it declares for its start
- **`TaskProgressEvent`** — a running task reported progress, a percentage and a message, or replaced its view, including the result view a task reports just before it completes
- **`TaskCompletedEvent`** — a task finished, carrying what it stored: the live value for in-process subscribers, and the JSON `wireValue` for wired stores
- **`TaskFailedEvent`** — a task terminated with a failure

The stream completes when the run does, and errors with the run's failure.

A run's live stream exists only in the process executing it. The run records the executing
node's id as `JobRun.nodeId`, so remote watchers route their watch request to that node - in a
cluster, any node can serve the persisted runs and records, while the live stream comes from
the one node named on the run.

## Presenting a task

A task, or a nested definition, declares how a console shows it. Its icon is a key — one of `TaskIcons`, or another the console knows — set with `icon(...)` on the task or the definition, or `@Task(icon = ...)` on a task method:

```java
.task(Tasks.fromCallable("Sync project source", syncSource)
           .icon(TaskIcons.GIT))
```

The icon is a fact of the definition, recorded on the task's `TaskRecord` from discovery, so a watcher shows it before the task runs. A key the console does not know shows its default icon.

A task's detail pane shows a `TaskView`: the key of the component that renders it, and the data that component renders. A view is built through a `TaskViewKind`, which binds the key to the data's type, so a view of one kind cannot be built with another kind's data. Each domain module keeps the kinds its consoles render in one constants class:

```java
public static final TaskViewKind<WorkloadLog> WORKLOAD_LOG = new TaskViewKind<>("workloadLog");
```

A task declares the views it shows, and the latest one it produced is its current view:

```java
.task(Tasks.fromCallable("Sync project source", syncSource)
           .icon(TaskIcons.GIT)
           .startView(DeployTarget.class, target -> WORKLOAD_LOG.of(new WorkloadLog(target.syncWorkloadId()))))
.task(Tasks.fromCallable("Resolve artifacts", resolveArtifacts)
           .store(Store.state(ARTIFACTS))
           .resultView(PROJECT_ARTIFACTS::of))
```

- **`startView(Source.class, source -> …)`** — shown from the moment the task starts, for following what the task does while it runs. Just before the task executes, the value of the source type is looked up in the job scope the way `@Autowired` looks it up, so the data a live view needs must be in the scope when the task starts. A value the scope does not hold fails the task. The class names the source because Java erases a lambda's parameter type.
- **`resultView(Result result -> …)`**, or **`resultView(Source.class, (Result result, Source source) -> …)`** — shown once the task completes, built from its result: the value it returns, or the value a returned `Future`, `CompletionStage` or `Publisher` completes with. The producer names the result's type — as a method reference does, or as a lambda's declared parameter type — since the task's own type parameter is the future's; a result of another type fails the task. The view is reported as the task's last view, as `TaskReporter.view` reports one, and the task then completes with its result unchanged.
- **`TaskReporter.view(view)`** — replaces the view while the task runs, from inside the task body; see [Reporting progress](#reporting-progress).

A view reaches watchers on the task's own events — `TaskStartedEvent.view` and `TaskProgressEvent.view` — and the task's `TaskRecord` keeps the latest one in `view`, written whenever it changes, so a finished run, or one whose node left mid-task, shows what the task last showed. A failed task keeps the view it showed when it failed. A view's data is serialized as JSON when the view is produced, and reaches every watcher of the run, so it must never carry secrets. A producer that throws, or data that does not serialize, fails the task.

## Reporting progress

Every job scope carries a `TaskReporter`, so a running task injects it like any other dependency and reports as it works — its progress, and, when what it shows changes, a new view:

```java
@Task(order = 1)
public void pullImage(TaskReporter reporter) {
    reporter.progress(30, "downloading layers");
    reporter.progress(80, "extracting");
}
```

Each report reaches watchers as a `TaskProgressEvent` attributed to the reporting task; a report that only replaces the view carries no percentage. Reports attach to the task in flight on the calling thread's Vert.x context — the run's own, where the task body executes and where the callbacks of futures bound to it are dispatched until the task's result has been awaited — so a report made from a callback of the task's own `Future` belongs to the task, and one made from a thread the task spawned itself is dropped. Progress is stream-only — it is not persisted with the run's records; a view is. Run-level progress needs no reports at all: watchers compute it from the discovered task tree and the completion events.

## Resuming a run

A `FAILED` or `CANCELLED` run can be resumed with a definition whose `name` and `version` match the recorded run:

```java
JobRunHandle resumed = jobService.resume(originalRunId, buildJob());
```

The resumed run is a new run — with its own id and records, linked to the original through `resumedFrom` and owned by whoever owned the original. Tasks the original run completed are handled by their `StoreType` as described above: skipped, re-run or reloaded, or replayed. A replayed `STATE` task builds its declared views from the scope and the replayed value; a skipped task, or a replayed one that declares no view, keeps the view the original run's record left it showing. A task that produced dynamic tasks re-executes so the dynamic structure is regenerated; the regenerated tasks then consult the original run's records at their own paths.

## Run records

Every run persists a `JobRun` — name, version, owner, status, timestamps, error, `resumedFrom`, and the `nodeId` of the executing node — and one `TaskRecord` per task: its `taskPath`, description, icon, status, timestamps, `storeType` and `storedName` (recorded from discovery when the definition names the store, so a watcher can tell the tasks apart before they complete), the serialized `STATE` value in `stateValue`, the wired value in `wireValue`, the latest view in `view`, and the failure message when it failed. The records are the run's durable history: what a dashboard renders after the event stream is gone, and what a resume replays from.

The ledger is written ahead of execution. Each transition is acknowledged by the store before the run moves past it: the `JobRun` and the `PENDING` records of the task tree before the first task starts, a task's `RUNNING` record before its body executes, its `COMPLETED` or `FAILED` record before the next task starts, and the terminal records before the event stream terminates — so a subscriber that sees the stream end can read the final ledger immediately. A node that goes down mid-run therefore leaves a `RUNNING` run whose records name exactly the task that was in flight, rather than losing the run. Every node watches the cluster membership, and a run still `RUNNING` on a node that is no longer a member is marked with the condition `SERVER_NODE_LEFT` on its `state.conditions`, since no node will report its end; the deployment that made the run, named in `state.parent`, is told, and its worker runs the deployment again. A run's terminal status is written in place, leaving that state as it is, and entered in the `kinotic_watch_event` ledger.

## Watching a run remotely

`JobService.watchRun(jobRunId)` attaches to a run executing in this process, replaying it from the start; it returns an empty stream for a run that has finished or never started, and subscribing never starts one. `JobMonitoringService` publishes that stream, and the records behind it, to remote callers in the management-api zone. Each node publishes its own instance, scoped by its node id: the finders are `@ScopeOptional`, so any instance answers an unscoped call, while `watch` must be invoked with the scope recorded on `JobRun.nodeId` — the node whose process holds the live stream:

```java
@Publish
public interface JobMonitoringService {

    @Scope
    String nodeId();

    @ScopeOptional
    Future<Page<JobRun>> findJobRuns(Pageable pageable);

    @ScopeOptional
    Future<JobRun> findJobRun(String jobRunId);

    @ScopeOptional
    Future<Page<TaskRecord>> findTasks(String jobRunId, Pageable pageable);

    Flux<JobRunEvent> watch(String jobRunId);

}
```

Every call is authorized against the run's recorded owner: an organization or application participant sees only the runs its organization owns, a system participant sees every run. Events cross the wire as JSON carrying a `type` discriminator, and a `TaskCompletedEvent` arrives carrying only its `wireValue` — the live `storedValue` never leaves the executing process:

```json
{
  "type": "taskCompleted",
  "taskPath": "0/3",
  "storeType": "STATE",
  "storedName": "runtimeWorkloadId",
  "wireValue": "wl-8f21"
}
```

A run that is no longer live is rendered from `findJobRun` and `findTasks` alone, so a watcher that reaches a finished run sees the same history the stream would have delivered. The records `findTasks` returns carry a task's value only as its `wireValue`; their `stateValue` and `stateValueType` are cleared, so durable state a task did not wire stays on the server.

## System jobs

A system job is a grind job the platform's operators start on demand. Each is a Spring bean implementing `SystemJob`, whose one method builds a fresh, named and versioned definition for each run; its name identifies the job and is recorded on every run, so it must be unique among the platform's system jobs:

```java
@Component
@RequiredArgsConstructor
public class WorkloadRetentionJob implements SystemJob {

    private final WorkloadRetentionSweeper sweeper;

    @Override
    public JobDefinition createJobDefinition() {
        return JobDefinition.create("Deletes the records and logs of workload runs that ended more than 30 days ago")
                            .name("workload-retention-sweep").version("1")
                            .task(Tasks.fromCallable("Delete expired workloads", sweeper::sweep));
    }
}
```

`SystemJobService`, published in the system zone, lists them and starts them:

```java
@Publish
public interface SystemJobService {

    Future<List<SystemJobDescriptor>> findSystemJobs();

    Future<JobRun> startSystemJob(String name);

}
```

`findSystemJobs` describes each job by its definition's `name`, `version` and `description`, ordered by name. `startSystemJob` runs the named job on behalf of the platform (`JobOwner.system()`) on the node that received the call, and completes with the `JobRun` once the run and its task ledger are recorded; it fails for a name no job has. From then on the run is an ordinary job run: listed, read and watched through `JobMonitoringService`.

The system console's **System jobs** page, under Platform, lists the jobs with a **Run** button each, which asks for confirmation, starts the run and opens its page, and lists below them the runs the platform owns. A run's page shows the run as the deployment pages do — its top-level tasks as a pipeline and its whole task tree, including every task a task generated as the run went.

### Workload logs

A step that runs a platform workload shows the workload's console log on its row, the way a deployment's steps do: open while the step runs, following new lines once **Follow** is pressed, and readable afterwards from the run's history. The step declares the log as its start view, built from the scope value that holds the workload's id, which must therefore be in the job scope when the step starts (see [Presenting a task](#presenting-a-task)):

```java
.task(Tasks.fromCallable("Run the check's VM", runWorkload)
           .startView(CheckTarget.class, target -> TaskViews.WORKLOAD_LOG.of(new WorkloadLog(target.workloadId()))))
```

The log is read in the organization that owns the run: for a system job, the platform's own log tenant.

The platform ships one system job:

| Name | What it does |
|---|---|
| `workload-retention-sweep` | Runs the [workload retention](/platform/configuration#workload-retention) sweep now |
