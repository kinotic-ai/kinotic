## Overview

Every organization's developer-side access lives in the platform's authorization store: who may view, edit or delete each application, project and entity definition. A grant gives a user or a group a role on a resource, and the role's permissions reach the resource and everything inside it, so where a grant is made decides what it covers. The console manages all of it through `PermissionService`, published in `management-api` for an organization's members; every function derives the organization from the caller, and a role, a group, a user or a resource it names must belong to that organization.

## Permissions

A permission is named for a resource type and an action: `project_can_edit`, `entity_definition_can_delete`, `application_can_view`. The platform's services declare them, so the catalog `findPermissions` returns is whatever the running release publishes, grouped by type; adding a function to a service adds its permission on the next release. The derived permissions imply each other, deleting implies editing and editing implies viewing, and a named permission such as `can_report` stands alone unless its service says otherwise.

## Roles

A role bundles permissions. The model defines a built-in viewer, editor and admin for every resource type, named `<type>.viewer`, `<type>.editor` and `<type>.admin`: the viewer holds the type's reading permissions, the editor everything but deleting, and the admin everything on the type and on everything inside it. `organization.admin` is therefore the organization's administrator, and `application.developer` holds everything inside an application without the application's own permissions. Built-in roles cannot be changed.

A custom role is defined by an organization from the catalog, with `saveRole`: a name, a description and the permissions it bundles. Changing a role's permissions changes every grant of it at once. A role is deleted with `deleteRole` once no grant holds it; a grant is revoked where it was made.

## Groups

A group collects an organization's members so one grant reaches all of them: `saveGroup`, `addGroupMember` and `removeGroupMember` manage it, and a grant made to a group reaches whoever is in the group at the time of a check. A group is deleted with `deleteGroup` once no grant holds it.

## Grants

`grant` gives a user or a group a role on the organization, or on an application, a project or an entity definition inside it; `revoke` takes it back where it was made. The subject holds every permission the role bundles on the resource and on everything inside it:

| Wanted | Grant |
|---|---|
| Sally can modify project A but not B | `project.editor` on project A |
| Marcus can work with every project of Atlas CRM | `application.developer` on the application |
| Priya can work with every project of every application, including ones created later | `application.developer` on the organization |
| QA can view every project of the organization but edit none | `project.viewer` on the organization, with the group as the subject |

`findGrants` lists the grants that reach a resource: those made on it, then those made on each ancestor up to the organization, each naming the resource it was made on, so the console shows an inherited grant with a link to where it was made.

## Reading access

`listAccessible` returns the resources of a type the caller holds a permission on, through any grant that reaches them, so a list page can read only what its viewer may see; it accepts the engine's cache window. `explain` answers whether a subject holds a permission on a resource and names the grants it holds the permission through: each one a role bundling the permission, made to the subject or to a group the subject is in, on the resource or on an ancestor. It asks the engine for a consistent answer, so it reflects a grant made or revoked a moment ago. A permission held through nothing a grant explains, such as a membership, is allowed with no grant named.

## Where the data lives

The engine holds the graph: a role's permissions, a group's members and every grant are relationships in the platform store, and a check answers from them through the generated model. Elasticsearch holds only the names and descriptions of custom roles and groups, in `kinotic_role` and `kinotic_group`. Enforcement of these grants at the gateway, on each request a member makes, is the next piece of the authorization layer; today the grants are made, listed and explained through the service.
