## Overview

Every organization's developer-side access lives in the platform's authorization store: who may view, edit or delete each application, project and entity definition, and who may manage the organization's members, machines, integrations and access. A grant gives a user or a group a role on a resource, and the role's permissions reach the resource and everything inside it, so where a grant is made decides what it covers. The console manages all of it through `PermissionService`, published in `management-api` for an organization's members; every function derives the organization from the caller, and a role, a group, a user or a resource it names must belong to that organization. Every request a member makes is checked against these grants where it enters the platform, so a grant is all it takes for a member to act and a revocation all it takes to stop them.

## Permissions

A permission is named for a resource type and an action: `project_can_edit`, `entity_definition_can_delete`, `application_can_view`, `organization_can_manage_members`. The platform's services declare them, so the catalog `findPermissions` returns is whatever the running release publishes, grouped by type; adding a function to a service adds its permission on the next release. The derived permissions imply each other, deleting implies editing and editing implies viewing, and a named permission such as `can_report` stands alone unless its service says otherwise.

The organization's own permissions are what its members manage rather than what they build: `can_view_members` and `can_manage_members` for the members and invitations, `can_view_machines` and `can_manage_machines` for the machines, `can_view_integrations` and `can_manage_integrations` for the GitHub installations, `can_view_access` and `can_manage_access` for the roles, groups and grants, `can_view_telemetry` for the logs, metrics and traces, and `can_view_jobs` for the job runs.

## Roles

A role bundles permissions. The model defines a built-in viewer, editor and admin for every resource type, named `<type>.viewer`, `<type>.editor` and `<type>.admin`: the viewer holds the type's reading permissions, `can_view`, `can_read`, `can_search` and every `can_view_<something>`, the editor everything but deleting, and the admin everything on the type and on everything inside it. `organization.admin` is therefore the organization's administrator, and `application.developer` holds everything inside an application without the application's own permissions. Built-in roles cannot be changed.

The member who creates an organization by signing up is bound as its administrator. An organization a migration seeds, such as the one the end-to-end tests use, records its creator the same way, and the management server binds that creator as the administrator when it starts and finds the organization has none; an organization whose administrator was revoked is left as it is.

A custom role is defined by an organization from the catalog, with `saveRole`: a name, a description and the permissions it bundles. Changing a role's permissions changes every grant of it at once. A role is deleted with `deleteRole` once no grant holds it; a grant is revoked where it was made.

## Groups

A group collects an organization's members so one grant reaches all of them: `saveGroup`, `addGroupMember` and `removeGroupMember` manage it, and a grant made to a group reaches whoever is in the group at the time of a check. A group is deleted with `deleteGroup` once no grant holds it.

## Grants

`grant` gives a user or a group a role on the organization, or on an application, a project or an entity definition inside it; `revoke` takes it back where it was made. The subject holds every permission the role bundles on the resource and on everything inside it:

| Wanted | Grant |
|---|---|
| Sally can modify project A but not B | `project.editor` on project A |
| Marcus can work with every project of Atlas CRM | `application.developer` on the application |
| Priya can work with every project of every application, including ones created later | `application.developer` on the organization |
| QA can view every project of the organization but edit none | `project.viewer` on the organization, with the group as the subject |

`findGrants` lists the grants that reach a resource: those made on it, then those made on each ancestor up to the organization, each naming the resource it was made on, so the console shows an inherited grant with a link to where it was made.

## Reading access

`listAccessible` returns the resources of a type the caller holds a permission on, through any grant that reaches them; it accepts the engine's cache window. The platform's own listings read it before they query: `ApplicationService` lists, counts, searches and finds by id only the applications the caller may see, which are the ones the caller may view and the ones containing a project or an entity definition the caller may view, and `ProjectService` lists, counts and searches only the projects the caller may view and those containing an entity definition the caller may view. A member granted `project.editor` on one project therefore sees that project's application and, inside it, that project alone; an application or a project the member may not see is absent from a listing and answered as not found by id, and everything else the member asks of a hidden project is refused as before. `explain` answers whether a subject holds a permission on a resource and names the grants it holds the permission through: each one a role bundling the permission, made to the subject or to a group the subject is in, on the resource or on an ancestor. It asks the engine for a consistent answer, so it reflects a grant made or revoked a moment ago. A permission held through nothing a grant explains, such as a membership, is allowed with no grant named.

## Enforcement

A request is checked once, where the platform stamps the caller onto it: the STOMP gateway, for a request a client sends, and the MCP endpoint, for a tool call. Both pass the request's destination, the caller, and the body to the same authorizer before anything is sent, and a refusal is answered to the caller as an `AuthorizationException`, with the permission and the object it was refused on; a tool call gets it as the tool's error result. Hops inside the platform carry the caller's participant and are not checked again, so a request that cascades through several services is authorized by the check at its entry.

The check is the one the function's contract declares. The authorizer reads the contract of the service a request addresses from the service directory once and keeps it for five minutes, resolves the object the function's check names from the request, and asks the engine whether the caller holds the permission on it: the object's id is read from the body with a parse that stops at it, at the parameter's position in a client's request or by the parameter's name in a tool call, and down a property path such as `entity.id`; a reference to the caller's scope, such as `{@organizationId}`, is read from the caller. A check on a scope level the caller's scope stops above is made on the caller's own level: an organization member asking for an application's projects, or re-syncing their index, is checked for the permission on the organization, which carries the permissions of everything inside it. A request that names no object its check needs is refused without asking the engine, as is one whose body no id can be read from.

A delegate, such as a session the CLI holds for a member, is checked as the member it acts for. A function whose contract declares no check, and a service the directory holds no contract for, pass on the zone rules alone: a client reaches only the zones its participant may address, and nothing more is asked. An application's end users and the platform's operators also pass on their zones for now; their stores and the platform's own resources are the next pieces of the authorization layer.

A server reports itself healthy only once the platform store runs a model, since until then every checked request is refused.

A function's check normally answers from the engine's caches, which may lag a change by a moment. A function declared `consistent`, one where a stale allow would be a security event, such as removing or disabling a member or rotating a machine's secret, is answered from the store itself.

## Declaring what a function does

A service declares its resource once, with `@AuthzResource`, and the check of each function is derived from the function's name and parameters: a `find`, `get`, `count`, `search` or `list` function needs `can_view`, a `save`, `update` or `set` function `can_edit`, a `delete` or `remove` function `can_delete`, and a `create` function `can_edit` of the type on the parent the argument names. The object is the resource id the function names: a parameter called `id` or `<type>Id`, or the `id` of an argument of the resource type; a function naming none is checked on the parent, read from the argument naming it or from the caller's scope.

A function the derivation cannot read is declared with `@AuthzCheck`: `permission` names a permission of its own, such as `can_deploy` or `can_view_members`, `resource` and `objectId` name another object, as `{registration.id}` or `{@organizationId}` do, `implies` names the permissions it carries, and `consistent` asks for the consistent answer described above. A service whose functions act on the caller's own organization names that object once, with `objectId` on `@AuthzResource`: every function is checked on it, whatever its arguments carry, unless it declares its own object, so each function declares only its permission. A function any caller the zone admits may call, such as a listing of the caller's own access, is declared `zoneOnly` and published with no check. A resource service's function that derives no check and declares none fails the service's registration, so no function of a resource service goes unchecked.

Machines take part the same way: the machines a project's deployment provisions for its workloads are bound as editors of the project when they are created, which is what the sync workload needs to record artifacts and run migrations, and the runtime to publish the project's services.

## In the client

`@kinotic-ai/management-api` mirrors the service as `Kinotic.permissions`, an `IPermissionService` with the same functions over the same models: `RoleDefinition`, `Group`, `Grant`, `Subject` with its `SubjectKind`, `Resource` and `AccessExplanation`. The console is built on it.

## Where the data lives

The engine holds the graph: a role's permissions, a group's members and every grant are relationships in the platform store, and a check answers from them through the generated model. Elasticsearch holds only the names and descriptions of custom roles and groups, in `kinotic_role` and `kinotic_group`.
