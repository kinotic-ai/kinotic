---
title: Multi-Tenancy
description: Multi-tenant data isolation in Kinotic with automatic tenant filtering.
---

Kinotic supports multi-tenant data isolation at the persistence layer. Data from different tenants is stored together but automatically filtered so each tenant only sees their own data.

## Defining a Multi-Tenant Entity

Add `@TenantId` to a field and set the entity to `MultiTenancyType.SHARED`.

```typescript
import { Entity, AutoGeneratedId, TenantId, MultiTenancyType } from '@kinotic-ai/persistence'

@Entity(MultiTenancyType.SHARED)
export class Person {
    @AutoGeneratedId
    id: string | null = null

    @TenantId
    tenantId: string = ''

    firstName: string = ''
    lastName: string = ''
}
```

The `@TenantId` field is populated automatically based on the authenticated user's tenant context. You do not need to set it manually when saving entities.

## Where a user's tenant comes from

Declaring the entity is only half of it. A user's tenant is assigned when the user is created, by one of the ways into a tenant the owning application enables — its `onboarding` mechanisms. An application enabling none leaves every user sharing one tenant-less set of data.

| Mechanism | Who triggers it | What assigns the tenant |
| --- | --- | --- |
| `TENANT_PER_USER` | The platform, as each user is created | A tenant of its own for every user, named for the user, so each user's `SHARED` rows are isolated from every other user's; the user is bound as its administrator, so it reads and writes its rows from the start. A user created into a tenant that exists fails, since the application holds one user per tenant. Exclusive with the other two |
| `TENANT_SIGN_UP` | A new customer at the application's own sign-up page | `POST /api/auth/app/signup` on the application's API host emails a verification link into the application's primary UI, and `POST /api/auth/app/signup/complete` creates the tenant, named by the customer, the customer as its first user, and makes the customer the tenant's administrator |
| `TENANT_INVITE` | A tenant's administrator, from the application's own pages | `TenantMemberService.inviteMember` emails an invitation into the administrator's tenant; the invitee accepts as an organization's invitee does, into that tenant |

An organization's members can also invite into a tenant from the portal, with `MemberService.inviteMember` naming the tenant, whatever the application enables. Every tenant is a record the platform keeps: its name, which the tenant's administrator may change through `TenantService.rename`, and the user it was created for.

A tenant's administrator can also choose an identity provider for the tenant, through `TenantService.configureSso`: the provider's kind, client id and authority, with a client secret named by reference to one an operator stores or left out for a public client, and the role a user the provider signs in for the first time is granted on the tenant. From then on the tenant's users sign in through it from the application's login page by the tenant's id, and whoever the provider vouches for arrives in the tenant without an invitation — the usual SaaS shape, where a customer signs up, configures SSO, and every colleague follows through it. `removeSso` takes the provider away again.

| Application `onboarding` | Entity | Result |
| --- | --- | --- |
| none | `MultiTenancyType.NONE` | One shared dataset — every user sees every other user's rows |
| any | `MultiTenancyType.NONE` | Still one shared dataset; the tenant has nothing to act on |
| none | `SHARED` + `@TenantId` | Users have no tenant, and writes fail with `tenantId cannot be null or blank for shared multi tenancy` |
| any | `SHARED` + `@TenantId` | Each tenant's users isolated in their tenant |

Choose the mechanisms when the application is created — `createApplicationIfNotExist` takes them as an argument — and change them afterwards from the portal, under **Application → Settings → Sign-in and tenancy**. `TENANT_SIGN_UP` needs a primary UI, since the verification link opens there.

`TENANT_PER_USER` applies to users created while it is enabled. Existing users are never backfilled, so enabling it on an application that already has users leaves those users without a tenant, and every write they make to a `SHARED` entity fails. Settle it before the application has users.

## Who may read a tenant's rows

A tenant is also where an end user's access is granted. A user holds nothing on a definition's rows until the application grants it a role through `ApplicationAccessService`, on the definition within its tenant for those rows alone, on its tenant for every definition's rows there, on the definition for its rows in every tenant, or on the application for everything: `tenant.admin` on the user's tenant is the grant for a user who owns its tenant's data, which the platform makes for an application isolating each user, and a user granted nothing is refused every read and write. See [Access Control](/platform/access-control) for the roles an application's store defines and how a request is checked against them.

## Tenants and services

A tenant comes from the authenticated participant, and only an application-scope participant carries one. A microservice running in a project's deployment connects at organization scope, so it cannot read or write a `SHARED` entity through the tenant-scoped repository — it uses the admin repository below, naming the tenants it means to act on. Per-user writes driven by the user belong on a client connected as that user.

## Tenant-Isolated Repository

The standard generated `Repository` automatically filters all operations to the current tenant. No additional configuration is needed.

```typescript
const service = new PersonRepository()

// Only returns people belonging to the current tenant
const people = await service.findAll({ page: 0, size: 10 })
```

All CRUD operations (save, find, update, delete, search, count) are scoped to the current tenant transparently.

## Admin Repository

When you run `kinotic sync` on an entity with a `@TenantId` field, the CLI generates both a tenant-scoped repository (`PersonRepository`) and an admin repository (`PersonAdminRepository`) that can access data across tenants. The admin repository is useful for administrative dashboards, reporting, and cross-tenant operations.

```typescript
const adminService = new PersonAdminRepository()
```

### Access All Tenants

```typescript
const allPeople = await adminService.findAll(['*'], { page: 0, size: 10 })
```

### Access a Specific Tenant

```typescript
const tenantPeople = await adminService.findAll(['tenant-123'], { page: 0, size: 10 })
```

### Access Multiple Tenants

```typescript
const multiPeople = await adminService.findAll(['tenant-123', 'tenant-456'], { page: 0, size: 10 })
```

## Tenant Selection

Admin repository methods accept a tenant selection array as the first argument:

| Selection               | Behavior                              |
|-------------------------|---------------------------------------|
| `['*']`                 | Access data from all tenants          |
| `['tenant-123']`        | Access data from a single tenant      |
| `['tenant-123', 'tenant-456']` | Access data from multiple tenants |

## Security Considerations

A participant that belongs to a tenant is confined to it. Through the admin repository, including its [named queries](/apps/persistence/named-queries#admin-repository-queries), it may select only its own tenant; naming another tenant, or `['*']`, is refused with an authorization error. On save, a blank `@TenantId` is filled with the participant's tenant and any other value is rejected. Selecting other tenants is possible only for a participant without a tenant, which is how a microservice in a project's deployment connects (organization scope), and such a participant must name the tenant of every entity it saves.

The standard tenant-isolated repository is the default and should be used for regular application logic.
