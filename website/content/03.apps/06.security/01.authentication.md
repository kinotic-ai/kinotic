## Overview

Kinotic supports multiple authentication methods to secure your applications. Every connection to a Kinotic server requires authentication — the platform identifies the caller and establishes a session before any service calls are allowed.

### Authentication Methods

- **Email and Password** — Built-in user management with secure credential storage, offered once your organization admin adds it as one of the application's sign-in providers. Ideal for getting started quickly or for applications that manage their own user base.
- **OIDC Providers** — Connect any standard OpenID Connect provider including Google, Microsoft, Okta, and others. Your organization admin enables OIDC configurations for your application; Google and Microsoft can be managed by Kinotic, with no setup, or use your own credentials.
- **Sign-up** — New people can create their own account, through a provider or with an email and a password verified by email, when the application turns it on.

This page covers what an application developer needs to know. For the platform-level model behind these mechanisms — scope isolation, the `OidcConfiguration` entity, signup and login flows — see [System Security](/platform/system-security) and [Organization Management](/platform/organization-management).

### Scoped Authentication

Authentication happens at the **WebSocket upgrade (handshake)**, not in a STOMP CONNECT frame. Every authentication carries a **scope** that identifies which layer the caller is authenticating against. Scope is structural — it is determined by which of two optional ids are supplied:

| `organizationId` | `applicationId` | Resulting scope |
|---|---|---|
| absent | absent | `SYSTEM` |
| present | absent | `ORGANIZATION` |
| present | present | `APPLICATION` |

For application developers this is always the `APPLICATION` scope, so both ids are supplied: your organization's id plus your application's id. Scope isolation ensures users are authenticated against the correct user pool — a user in Application A cannot access Application B, even if both applications use the same OIDC provider.

## Connecting with Email and Password

In Node, pass a `BasicCredentialsResolver` carrying the credential and scope values (`clientId`, `clientSecret`, `organizationId`, `applicationId`); they are presented as headers on the WebSocket upgrade:

```typescript
import { BasicCredentialsResolver, Kinotic } from '@kinotic-ai/core'
import { ensureNodeWebSocket } from '@kinotic-ai/core/node'

ensureNodeWebSocket()
await Kinotic.connect({
    credentials: new BasicCredentialsResolver('user@example.com', 'password', 'my-organization', 'my-application')
})
```

The constructor is `BasicCredentialsResolver(clientId, clientSecret, organizationId?, applicationId?)`. The `clientId` is your user's email and `clientSecret` is the password — or a machine identity's id and provisioned secret. The platform looks up the user by email within your application's scope, verifies the password against a securely stored bcrypt hash, and establishes a session.

Your application's users and machines connect to the app server, at your application's API host (the `VITE_KINOTIC_HOST` a UI build receives, `<organizationId>--<applicationId>` under the platform's application domain) or at the app server's own address. The app server authenticates only application identities and the runtime workloads of your organization's applications: organization and system credentials fail there as invalid, and on an application's API host so do the credentials of any other application.

With no `credentials` at all, `Kinotic.connect()` resolves through the default chain: the `KINOTIC_CLIENT_ID` / `KINOTIC_CLIENT_SECRET` (plus optional `KINOTIC_ORGANIZATION_ID` / `KINOTIC_APPLICATION_ID`) environment variables, then the browser session. Server settings resolve the same way — the `server` option, the `KINOTIC_SERVER_HOST/PORT/USE_SSL` variables, the page's own location in a browser, then the management server at `https://api.kinotic.ai`, so an application's client names its API host. To pin the server explicitly, pass it alongside the credentials:

```typescript
await Kinotic.connect({
    server: { host: 'kinotic.example.com', useSSL: true },
    credentials: new BasicCredentialsResolver('user@example.com', 'password', 'my-organization', 'my-application')
})
```

Absent `server` fields fall through to the environment. With nothing stating `useSSL`, `{ host }` alone means TLS on the scheme's default port, unless the host is loopback (`localhost`, `127.0.0.1`, `::1`), which means no TLS and port `58503`, the management server's gateway port — so a connection to a local app server names its port, `58505`, and a remote server reached without TLS names `useSSL: false`.

## Connecting with OIDC

For token-based authentication, pass a Bearer token via `BearerCredentialsResolver`. The resolver sends `Authorization: Bearer <token>` on every (re)connect; pass a supplier function to refresh a short-lived token before each connect:

```typescript
import { BearerCredentialsResolver, Kinotic } from '@kinotic-ai/core'
import { ensureNodeWebSocket } from '@kinotic-ai/core/node'

ensureNodeWebSocket()
await Kinotic.connect({
    credentials: new BearerCredentialsResolver(async () => await getToken())
})
```

A Kinotic-minted JWT already carries the `organizationId` / `applicationId` claims, so no scope headers are needed alongside it. The platform validates the JWT against the OIDC configurations enabled for your application, matches the token's email to a pre-existing user in your application's scope, and establishes a session.

### Browser applications

A browser UI does **not** supply credentials. It signs its user in, or up, over REST at its application's API host, the `VITE_KINOTIC_HOST` of [the UI build contract](/apps/application-structure/applications-and-projects#the-ui-build-contract), which sets a session cookie for that host, then connects to the same host with no credentials — the default resolution finds the session. The host names the application, so the UI never sends its organization or application id. Every call below takes `credentials: 'include'` and is made from a page that is one of the application's own UIs; the API host refuses a sign-in or sign-up from any other page with `403`.

A UI that offers sign-in serves a `/login` page; one that offers sign-up also serves a `/signup` page and the `/signup/verify` page the verification email links to. Both pages start by asking the API host what the login offers:

```
GET /api/auth/app/login/methods
→ 200 [ { "configurationId": "acme:orders", "type": "PASSWORD", "name": "Email and password", "provider": null, "signUp": true },
        { "configurationId": "4f1c…", "type": "OIDC", "name": "Google", "provider": "google", "signUp": true } ]
```

The answer is the login's sign-in providers, in the order to show them:

| Field | Meaning |
|---|---|
| `type` | `PASSWORD`: an email and a password, shown as the password form. `OIDC`: an identity provider, shown as one "Continue with `name`" button, branded by `provider` (`google`, `azure-ad`, `okta`), which starts a sign-in through `configurationId` |
| `signUp` | New people may sign up: for `PASSWORD`, with an email and a password, so the sign-up page shows its form; for `OIDC`, the provider creates the user of a person it verifies on their first sign-in, so its button belongs on the sign-up page too |

A login takes an email and a password only while the application has the **Email and password** provider (a `PasswordConfiguration`, below), so the list has a `PASSWORD` entry; otherwise `POST /api/auth/app/login` and a connection presenting an email and a password answer as for a wrong password.

```typescript
import { Kinotic } from '@kinotic-ai/core'

const env = import.meta.env
const server = { host: env.VITE_KINOTIC_HOST, port: parseInt(env.VITE_KINOTIC_PORT), useSSL: env.VITE_KINOTIC_USE_SSL === 'true' }
const api = `${server.useSSL ? 'https' : 'http'}://${server.host}:${server.port}/api/auth`
const post = (path: string, body: object) => fetch(`${api}${path}`, {
    method: 'POST',
    credentials: 'include',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(body),
})

// what the login offers, for both the /login and the /signup page
const providers = await (await fetch(`${api}/app/login/methods`, { credentials: 'include' })).json()
const password = providers.find(provider => provider.type === 'PASSWORD')

// /login, while the login takes a password: the password form
if ((await post('/app/login', { email, password })).status === 204) {
    await Kinotic.connect({ server })
}

// /login and /signup: one "Continue with <name>" button per provider; on /signup, only those with signUp
async function continueWith(provider: { configurationId: string }) {
    const start = await (await post(`/app/login/oidc/start/${provider.configurationId}`, {})).json()
    window.location.assign(start.redirect)
}

// /signup, while password?.signUp: 202 once the link is emailed, or, on a server that sends no email,
// 200 with the link to show (409: the email has an account, so sign in)
const started = await post('/app/signup', { email })
const link = started.status === 200 ? (await started.json()).verificationUrl : null
// show link when there is one; otherwise the person checks their inbox

// /signup/verify?token=…: the person chooses a password, and optionally a name, and is signed in
const token = new URLSearchParams(window.location.search).get('token')
const done = await post('/app/signup/complete', { token, password, displayName })
if (done.status === 204) {
    await Kinotic.connect({ server })
}
```

#### Signing in

The login page offers every method the application supports and lets the user choose: the password form, posting to `POST /api/auth/app/login`, which answers `204` with the cookie or a generic `401`, and a button for each provider. A button posts the provider's `id` to `POST /api/auth/app/login/oidc/start/:id`, whose answer carries the `redirect` to send the browser to. The provider returns the browser to `/` on the page that started the sign-in, signed in, or to that page's `/login` with an `error` parameter (`no_user`, `user_exists`, `user_disabled`, `email_not_verified`, `config_not_found`, …). An `email_not_verified` or `no_user` redirect also names the provider by its key in a `provider` parameter (`google`, `azure-ad`, `okta`, …), so the page can tell the user which provider to verify the email with, or which provider's account has no user. No endpoint takes an email before the user has chosen a method, so a login page cannot be used to learn which emails have a user.

`GET /api/auth/me` answers `204` while the page is signed in, and `POST /api/auth/logout` signs it out and ends the realtime connections the page's login established.

#### Signing up

A person gets a user of your application without an administrator adding them in two ways, each switched on by your organization administrator on the application's sign-in providers:

- **Through a provider.** A provider whose `signUp` is true makes a person it verifies a user on their first sign-in, from the provider's verified email and name. There is no separate sign-up call: the same "Continue with Google" button signs a new person up and an existing user in. A person whose email already has a user under another method is refused with `user_exists`, and signs in the way they did before. Microsoft lets the administrator of any directory set its users' email, so a Microsoft provider that admits every directory — managed by Kinotic, or your own credentials naming `common` or `organizations` — signs up a personal Microsoft account, or a work account whose token carries `xms_edov` (email domain owner verified) or `email_verified` as true; any other Microsoft account is refused with `email_not_verified` and joins by being added or another method. A Microsoft registration of your own emits `xms_edov` once you add it as an optional claim of the ID token in its Entra app registration. A provider naming one directory, your own or a tenant's, signs up that directory's users as its administrator set them.
- **With an email and a password.** While the `PASSWORD` provider's `signUp` is true — the application's **Email and password** provider has `createUserOnSignIn` on — the sign-up page posts `{email}` to `POST /api/auth/app/signup`; the email it sends carries only the application's name and the link. It answers `202` for every email, before anything is sent, and an email that already has a user is sent nothing, so the page cannot learn whether an account exists; tell the person to check their inbox. On a server that sends no email (`kinotic.domain.email.enabled` is `false`, as on a local server), it answers `200 {verificationUrl}` instead, with the link the email would have carried, so the page shows the link for the person to open, and `409` for an email that already has a user, who signs in instead. A page that handles both answers works on every server. The email is matched trimmed and lowercased. The email links to `/signup/verify?token=…` on the same UI the sign-up started from and is valid for 24 hours; while a link sent to the address is still valid, asking again sends nothing more (where no email is sent, it answers with the same link again), and once it has expired, asking again sends a new one. That page posts `{token, password, displayName}` to `POST /api/auth/app/signup/complete`, where the optional `displayName`, at most 200 characters, is the user's name: it is asked for here, of the person who holds the email, so whoever asked for the link cannot choose it. The call creates the user and answers `204` with the session cookie. It answers `400` for an unknown, used or expired token, or one sent for another application, a missing password or a longer name, `403` from a tenant's site or once the application no longer offers password sign-up, and `409` when the email got a user meanwhile, in which case the person signs in instead.

The sign-up endpoints answer `403` while the application does not offer password sign-up, and from a tenant's site.

Every new user ends up in a tenant. An application signs people up at its own login only while the system manages its tenants (`TenantManagement.SYSTEM`), which gives each new user a tenant of their own; every provider's `signUp` is false at the login of an application whose tenants their administrators manage. There a person joins a tenant by being added to it ([below](#user-management)), or through one of the tenant's own providers that signs people up, at the tenant's login (below).

### Signing in to a tenant

An application whose tenants its administrators manage gives each tenant a login of its own. A page served at one of the tenant's sites, `<tenantId>--<applicationId>--<uiName>` under your organization's subdomain of the sites domain (see [Multi-Tenancy](/apps/persistence/multi-tenancy#tenants-and-their-sites)), signs in to that tenant with the same calls as above: the API host reads the tenant from the page's host, so `/app/login/methods` lists what the tenant's login offers — the tenant's own providers, then the application's — and `/app/login` admits only the tenant's users. Only the tenant's own providers can sign people up there, into the tenant; the application's providers sign in the tenant's existing users, and password sign-up is not offered. The tenant's login takes an email and a password while the tenant's own **Email and password** provider, or the application's, is enabled; a user's password signs in wherever their own tenant's, else the application's, provider is enabled. Deleting the application or the tenant deletes its **Email and password**. A page that is not one of the tenant's sites, such as a UI running locally, names the tenant instead, with `?tenantId=` on the `GET` and the start, and `tenantId` in the login body; the API host answers `404` for a tenant the application does not have, and `403` when a tenant's site names another tenant.

### Sign-in providers

Your organization administrator adds the application's sign-in providers in the portal under the application's **Settings → Sign-in providers** tab, each an `ApplicationOidcConfiguration` (or a `TenantOidcConfiguration` for one tenant's login), or a product built on Kinotic saves them through `OwnedOidcConfigurationService.save`. **Email and password** is a provider of the same list, a `PasswordConfiguration` of the application's login or of one tenant's, saved through `OwnedPasswordConfigurationService.save`: a scope has at most one, `enabled` decides whether its login takes a password, and `createUserOnSignIn`, taken by the application's own only and only while the system manages its tenants, turns on password sign-up. For Google and Microsoft — the kinds `OwnedOidcConfigurationService.findManagedProviders()` lists — each provider chooses whose registration with the provider it signs in through, its `clientRegistrationType`:

| `clientRegistrationType` | Setup | Consent screen |
|---|---|---|
| `MANAGED` — managed by Kinotic | None: the provider signs in through Kinotic's own registration with Google or Microsoft | Kinotic's name |
| `OWN` — your own credentials | Register an OAuth client at the provider, give the configuration its client ID and secret (and for Microsoft the directory: a tenant id, or `common` / `organizations` for any account), and register the configuration's callback URL, `https://<organizationId>--<applicationId>.<app API domain>/api/auth/app/login/oidc/callback/<configId>`, which the tab shows | Your application's name and branding |

Okta, and Google or Microsoft for one tenant, always use your own credentials. Sign-in and sign-up behave the same either way. Switching a provider between the two is an edit of the same configuration, and its users stay the same users: a user is bound to the identifier the provider gives the person under every client it registers — Google's `sub`, Microsoft's directory and object ids — so a person who signed up under Kinotic's registration signs in under yours, and back. One exception: Microsoft identifies a guest (B2B) user by the directory they sign in to, and Kinotic's registration signs a guest in through their home directory while your own registration naming your directory signs them in through yours. A guest who signed up one way is therefore not recognized the other way, in either direction of a switch: their email already has a user, so the sign-in is refused with `user_exists`, or with `no_user` where the provider does not sign people up. A configuration using Kinotic's registration keeps any client ID and secret it holds, so switching back needs no new setup. Kinotic's registration is shared by every application that uses it, so a user who revokes it at the provider revokes it for all of them.

A provider's `createUserOnSignIn` is its `signUp`: on, it signs new people up where the scope admits them, as described above.

How a sign-in through a provider runs:

1. Your UI renders a button per provider the login offers; the button posts the configuration's id to the start at your API host, whose answer carries the URL to send the browser to
2. The provider returns the browser to the API host, which validates the provider's response, finds the user bound to the identity in your application, or in the tenant the sign-in is to, else claims the pending user an administrator added under the identity's email ([below](#user-management)), else creates it where the provider signs people up, and sets the session cookie. A provider using Kinotic's registration returns the browser to the app server's shared host instead, which validates the response, finds, claims or creates the user, and hands the sign-in to your application's API host under a single-use code, which completes only in the browser that started the sign-in; that host sets the cookie
3. The browser returns to `/` on the site that started the sign-in, which connects with the session; a sign-in that fails returns instead to the `/login` page of that site with an `error` parameter, so every UI that offers sign-in serves a `/login` route. A failure that no longer knows which site started it — the flow's session expired, or a shared registration's single-use code was refused with `handoff_invalid` — returns to the `/login` page of your application's [primary UI](/apps/application-structure/applications-and-projects#applications)

An AI assistant building the pages can ask what the login offers through the `ApplicationService.getLoginMethods` MCP tool, which answers what `GET /api/auth/app/login/methods` answers for the application's own login. Every identity provider is an `OidcConfiguration`, and the email and password a `PasswordConfiguration` — see [System Security](/platform/system-security) for how ownership is captured by the subtype.

## User Management

Besides signing up, an application's users are **added** by an administrator. Your organization administrator manages your application's users on the application's **Users** page in the portal: **Add user**, with the person's email, an optional display name, the tenant they join, picked by searching the application's tenants by the start of a name or id (`TenantService.findForApplicationByPrefix`), and a switch, on by default, that emails them an invitation (`MemberService.addApplicationUser`, taking an `AddApplicationUserRequest` of `email`, `displayName`, `applicationId`, `tenantId` and `sendInvitation`). The person becomes a user of the application at once, with no sign-in method, listed as *Pending* (the user's `pending`, as `MemberService.findApplicationUsers` lists it) until they first sign in, which claims the user in one of two ways:

- **Signing in through one of the application's providers** under the same email, at the application's login or, for a tenant's user, the tenant's: the identity is bound to the user as its first sign-in method, whether or not the provider signs people up. A provider that admits every directory claims the user only under an email the token proves, as for [signing up](#signing-up); a disabled user is refused with `user_disabled`. A user someone already signs in as is not claimed again, and a pending user of one tenant is not claimed at another tenant's login.
- **Accepting the invitation** with a password, where the user's login takes one — their tenant's, else the application's. The accept page sets the password and sends the person to your application's [primary UI](/apps/application-structure/applications-and-projects#applications), where they sign in with that email and password from then on; while the application has no primary UI, the page confirms the user instead. The first UI one of your projects publishes becomes the primary UI unless you have chosen one. The page also names the application's providers and links to the primary UI, where signing in through one of them claims the user as above.

The application must offer a way in before anyone is added: without an invitation, a provider at the user's login — their tenant's own or the application's; with one, a password at that login, or one of the application's own providers and a primary UI, since the invitation links to the primary UI, whose login offers those providers. *Send invitation* later is held to the same rule. Every user belongs to a tenant: an application whose tenants its administrators manage takes one of them, which the administrator must name, and one whose tenants the system manages takes none and gives the person a tenant of their own, as signing up does. *Send invitation* (`MemberService.sendInvitation(email, applicationId)`) sends a pending user the invitation they have again, or a first one; removing a pending user cancels their invitation.

Sign-in and sign-up are configured per application, by the organization in the portal or by any product built on Kinotic through the management API: the application's `PasswordConfiguration`, saved with `OwnedPasswordConfigurationService.save`, turns on sign-in with an email and a password, and with `createUserOnSignIn` sign-up with them, and each provider's `createUserOnSignIn` and `clientRegistrationType`, saved with `OwnedOidcConfigurationService.save`, say whether it signs people up and whose registration it uses. A builder that creates applications for its own users can create each one with `TenantManagement.SYSTEM`, add a Google provider managed by Kinotic with `createUserOnSignIn` on, add an email and a password when the owner wants it, and later save the same provider with `OWN` and the owner's client ID and secret.

For details on user and OIDC configuration management, see the [Organization Management](/platform/organization-management) platform guide.
