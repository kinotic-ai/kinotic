## Installation

Provisioned project repositories vendor the CLI as a dev dependency, so inside a
project the CLI is already available -- `bun run generate` runs it with no global
install. To use the CLI outside a project:

```bash
bun install -g @kinotic-ai/kinotic-cli@beta
```

## Commands

Project commands (`kinotic generate`, `kinotic sync`) locate the project by searching upward from the current directory for a `.config/kinotic.config.*` file, so they can be run from any directory inside the project.

### `kinotic login`

Log in to a Kinotic server and store credentials for subsequent commands. Runs the OAuth device-authorization flow: the CLI opens a browser once for you to approve, then stores a refresh token so later commands are non-interactive. The server you log in to becomes the default server for commands like `kinotic sync`.

```bash
kinotic login --server http://localhost:58503
kinotic login
```

**Flags:**

| Flag | Description |
|------|-------------|
| `-s, --server` | The Kinotic server URL to log in to. When omitted, the stored default server is used |

### `kinotic local`

Run Kinotic on this machine: its servers, the portal and system console, the Git server that holds your projects'
repositories, and the node your projects deploy to. The stack runs in Docker from the compose files bundled with
the CLI, at the Kinotic version that CLI release names; the node is the `@kinotic-ai/vm-manager` release it names,
which Bun downloads on first start and runs in the background. The stack's files, the node's process id and its
log live under `local` in the CLI's data directory (`~/.local/share/kinotic/local`). The
[Quick Start](/getting-started/quick-start) installs the CLI and runs `kinotic local up` in one line.

```bash
kinotic local up            # start Kinotic and the node; the first start takes a few minutes
kinotic local status        # each container's state, and whether the node runs
kinotic local logs node     # the node's log; name a container instead, or none for every container's
kinotic local down          # stop Kinotic and the apps it deployed, keeping its data
```

`kinotic local up` needs Docker running with Compose v2, and Bun to run the node. Each start downloads the newest
images of that version, and starts from those already on the machine when it cannot. The node runs on macOS on Apple
silicon, or Linux with KVM (`/dev/kvm`, which your user must be allowed to open, usually through the `kvm` group);
elsewhere Kinotic starts without one, and projects do not deploy. Once the servers answer, create your organization at
`http://localhost:9090/signup`. `kinotic local down` stops the node first, which stops and removes every app it
deployed on this machine, then the stack.

| Command | Flag | Description |
|---------|------|-------------|
| `kinotic local down` | `--delete-data` | Also delete everything Kinotic stored: its organizations, projects, data and deployed apps' files |
| `kinotic local logs [SERVICE]` | `-f, --follow` | Keep printing new lines until interrupted |

### `kinotic generate` / `kinotic gen`

Generate Repository classes from your entity definitions. This runs locally without connecting to the server, and fills in the implementations of [named query](/apps/persistence/named-queries) methods declared with `@Query`.

Each entity's C3Type schema is written as JSON to `.config/c3/entities/<namespace>.<name>.json`, and the named queries declared on a Repository to `.config/c3/queries/<RepositoryName>.json`. Removing the last named query from a Repository removes its queries file.

Every class decorated with `@Publish` under the project's `servicesPaths` gets a service definition: its functions, with the parameters a request carries and their types. The definitions are written to `ServiceDefinitions.ts` under `generatedPath`, a module the project imports so each service registers in the platform's service directory as it comes online.

```bash
kinotic generate
kinotic gen -v
kinotic gen --force
```

**Flags:**

| Flag | Description |
|------|-------------|
| `-v, --verbose` | Enable verbose logging |
| `-f, --force` | Force full regeneration, ignoring incremental change detection |

### `kinotic sync` / `kinotic synchronize`

Synchronize local entity definitions with the Kinotic server. This uploads your entity classes so the server can set up the backing data stores and register the entity services, and applies any pending [migrations](/apps/persistence/migrations) from the `./migrations` directory. The entities are synchronized into the project named by `projectId` in `.config/kinotic.config.ts`, which must already exist in Kinotic OS. It runs the same generation as `kinotic generate`, so the repository classes, `.config/c3` and the `ServiceDefinitions` module are refreshed as well; the service definitions reach the server from the runtime, as each service comes online, not from the sync. Requires a prior `kinotic login` against the target server.

```bash
kinotic sync -p
kinotic sync -p -v -s http://localhost:58503
```

**Flags:**

| Flag | Description |
|------|-------------|
| `-s, --server` | The Kinotic server URL. When omitted, the stored default server is used |
| `-p, --publish` | Publish each entity after save/update |
| `-v, --verbose` | Enable verbose logging |
| `--dryRun` | Enables verbose logging and does not save any changes to the server |
| `--force` | Force full regeneration, ignoring incremental change detection |
